# Working in this repository

Procedures and rules that hold across tasks. Facts that change (test counts, costs, what is
finished) belong in each component's README and in `design/`, not here.

## Orientation

- `design/DESIGN.md` is the architecture. `design/DECISIONS.md` records each decision with
  its alternatives and what would change it. Read both before changing behaviour.
- `contracts/` holds the interfaces between components. Components live in sibling
  directories and depend only on `contracts/` and on each other's published types.
- `research/` is background. Each file tags claims as verified, secondary or training
  knowledge; treat the last two as leads, not facts.

## Changing things

1. **Contracts first.** If a component needs an interface to change, change `contracts/`
   in its own commit, then the components. Never redefine a contract locally. If you are
   working inside one component and cannot change the contract, implement the closest
   faithful thing and record it under a "Contract issues" heading in that component's README.
2. **Decisions are recorded, not implied.** A choice between real alternatives gets an entry
   in `design/DECISIONS.md`: decision, alternatives, why, "would change if". When the owner
   reverses a decision, rewrite the entry and say that it replaces an earlier one.
3. **Keep the design text true.** When code or a decision diverges from `DESIGN.md`, update
   `DESIGN.md` in the same change. The published design page is generated from
   `design/artifact/viz-design.html`; update it when the design or its status changes.
4. **Every component has a README** with: what is implemented, what is not, how it was
   verified (commands and results), known risks. "Not implemented" is a required section.

## Evidence

- **Say what kind of number it is.** Measured here, measured on Cloudflare, or modelled.
  Print modelled costs and latencies as ranges and name the experiment that would settle
  them (`design/VERIFICATION.md` §4).
- **Counterfactuals, not single runs.** To claim A beats B, implement the same workload
  both ways, tune each side separately, make them read each other's output, and require
  identical results before comparing times. Record the tuning steps, including the ones
  that did not help. `bench/README.md` is the template.
- **Tests must have teeth.** After writing tests for a safety property, break the property
  in the source on purpose, confirm a test fails, restore the source, and list the mutants
  and which test caught each in the README. A mutant that survives is reported, not hidden.
  Apply mutants to a copy of the component in your scratch area, never in place in the shared
  tree: others commit and snapshot the tree while you work, and a mutant caught in a commit
  ships (one reached a pull request to `main` this way).
- **Snapshot only what is green.** A pull request to `main` takes each directory from a state
  its owner reported green (all its suites, with no mutation run or edit in progress), not
  from whatever is on disk.
- **Independent readers.** Anything viz writes in an open format (Parquet, Iceberg, the
  Prometheus API) is also read back by an implementation viz did not write.
- **Review before building on it.** Protocol changes get an adversarial review by someone
  who has not seen the reasoning; findings and dispositions go in `design/REVIEW.md`.
- Report what failed and what was skipped as plainly as what passed.

## Design changes

Anything that alters what a person sees or how they operate the interface is a design
change. The ground truth is `design-system/`: `project/tokens.json` for values,
`project/README.md` for rules, `project/method.md` for how to design, `project/review.md`
for the review rubric.

1. **Design against the system.** Token values only; component classes before new
   components; follow the build order in `method.md` (content, then type and space, then
   structure, then colour last, then states, then the second theme, then the text form).
2. **Run the checks.** `node design-system/tools/check.mjs <changed paths>` must pass: no
   literal colours, lengths, durations or opacity, and contrast holds if tokens changed.
   Component CSS is written in `design-system/src/components.css`; `bundle.css` and `dist/`
   are generated by `tools/build.mjs`. When a component uses a new colour pairing, add the
   pairing to the list in `check.mjs`: the check only covers what it is told about.
3. **Capture before and after images** with `design-system/tools/shots.mjs`: every changed
   view, both themes, 1440 and 400 px wide, same data and state. Commit the composed images
   under `design-system/reviews/<change>/compare/` and reference them by commit in the pull
   request description. A design pull request without before/after images is not ready.
4. **Compose before judging.** Components that look right alone can fail together. Render
   a realistic full screen, a dialog, an empty and an error state and a long table, in both
   themes, at 1500 and 400 px and with a coarse pointer, and judge those.
5. **Get an expert design review before merging.** The reviewer did not write the change
   and is not given the author's reasoning: they get the images, the running view and the
   design system, and return approve, approve with changes, or reject, with findings tied
   to the rubric and to an image. Record the verdict in the pull request, and keep the
   review under `design-system/reviews/<change>/`. A reject is re-imaged and reviewed again.
6. **Measure speed.** The budgets in the design system's "Responsiveness and feedback"
   section are requirements. A change that touches interaction attaches before and after
   measurements (input response, view change, first result paint) and how they were taken.
   Progress indicators show only measured work; never add a spinner or skeleton to cover a
   slow path, fix the path or say truthfully what is happening.
7. **Merge.** Once the verdict is approve and checks pass, the change may be merged
   without waiting for the owner. Blockers and majors are fixed and re-imaged first.
8. **Change the system in the same pull request** when a change needs a new token or
   component. `tokens.json` is the single source; `dist/` is generated and never edited.
   Republish the reference after the system changes.

## Durable Objects

- Storage is the only source of truth. Any in-memory state must be rebuilt from SQLite in
  the constructor; test it with `evictDurableObject`.
- Every SQL statement that touches tenant data names the tenant in its `WHERE` clause.
  Tenant identity comes from the credential, never from a header, path or body.
- A mutation and its change-log or outbox row go in the same transaction.
- Store whole batches as rows, never one row per sample: row writes are billed.
- One alarm per object, set to the earliest deadline, deleted when there is nothing to do.
  Alarm handlers are idempotent; alarms are at-least-once.
- Never hold `blockConcurrencyWhile` across R2 or network I/O.
- A request can have six outbound connections in flight, and that includes R2 binding
  reads. A Worker called through a service binding spends from its caller's six; a Durable
  Object has its own. To read R2 in parallel beyond six, fan out to Durable Objects.
- An R2 write takes about 0.17–0.4 s whatever its size up to 1 MB (a read takes about
  0.05 s), and writes share the six-in-flight limit. Never put a PUT on a request's
  acknowledgement path, and never issue one PUT per item in a loop: batch into one object,
  or spread writes over Durable Objects (`spikes/s5-r2-writes/`).
- An R2 range read costs about one round trip (tens of milliseconds) whatever its size
  below 1 MB: issue few, coalesced reads.
- Refuse rather than guess: a caller holding a stale watermark, epoch or incarnation gets an
  explicit status, not a best-effort answer.
- Overload returns a retryable status. Nothing is acknowledged and then dropped.

## TypeScript components

- `shard/` is the reference setup: `wrangler.jsonc`, `vitest.config.ts` using
  `cloudflareTest` from `@cloudflare/vitest-plugin`, and bindings typed by declaring
  `namespace Cloudflare { interface Env { ... } }` in `test/env.d.ts`.
- Tests run inside the Workers runtime. Use `evictDurableObject`, `runDurableObjectAlarm`
  and `runInDurableObject` from `cloudflare:test`; import `env` from `cloudflare:workers`.
- `npm test` and `npx tsc --noEmit` both pass before a change is done.
- Nothing that needs `eval` or `new Function` at runtime; Workers forbid it.

## The Cloudflare account

The environment provides `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. The account
also holds unrelated Workers, buckets and KV namespaces.

- **Only create, change or delete resources whose names start with `viz-`.** Never touch
  anything else in the account, including resources that happen to share a binding name
  (there is an unrelated KV namespace called `CONFIG`).
- The product is served under **`vis.bitcru.sh`**. Do not change DNS or routes for any other
  hostname in that zone.
- Never print, log or commit the token, an API key, or a Worker secret. Generate secrets at
  deploy time and set them with `wrangler secret put`.
- **The owner allows stage deploys** (2026-11-28, standing): a stage (`deploy/deploy.sh --stage
  <name>`, every resource named `viz-<stage>-…`, workers.dev only) may be deployed, exercised and
  destroyed without asking again, under the rules here (worst-case cost stated first, an expiry,
  deleted when the measurement is done, recorded in a spike README). Production deploys still go
  through `main` and the deploy workflow only.
- Experiments live under `spikes/<name>/`, each with a README that says what is deployed,
  what it costs, how to read the result, and how to delete it. Anything that runs on a
  timer must stop by itself at a deadline.
- Before deploying, state the worst-case cost. After deploying, record what was created.
- To load-test from inside Cloudflare, make each client its own Durable Object. A client
  outside Cloudflare, or one Worker fanning out through a service binding, measures the
  client and not the system.
- Delete dev and load-test deployments when the measurement is done, and say so in the
  spike's README. Do not put a secret on a command line where a process listing shows it.
- Usage and billing figures come from Cloudflare's analytics API, not from estimates; a
  number read from there is "measured on Cloudflare", and says for which window.

## Shared machine

Many builds may run at once on one machine with 16 GB of memory and 4 cores, and the
kernel kills processes when memory runs out.

- Build Rust with `-j 2`, run test runners with at most 2 workers, and keep any single
  process under about 1.5 GB. Scale a benchmark down and extrapolate rather than exceed it,
  and say that you did.
- Do not run two heavy jobs (a model checker, a large benchmark, a full Rust build) at the
  same time.
- If a run dies without a result, rerun it; never treat a missing result as a pass.
- Vitest caches transformed test files, with resolved absolute paths, in `node_modules/.vitest-cache`.
  A worktree whose `node_modules` is a symlink to another checkout's shares that cache and can load the
  other tree's files (a review of D77 found a worktree's tests loading the main checkout's
  `viz_engine.wasm`). In a worktree with linked `node_modules`, run vitest with `--no-cache` (or a
  cache directory of its own) for any run used as evidence.
- Stop servers you started when you finish.

## Licensing

- viz is Apache-2.0. Never copy, transcribe or port code, grammars, generated tables or tests
  from a project whose licence is incompatible with it (AGPL, GPL, SSPL, BUSL and similar,
  including Grafana Tempo, Loki and Mimir). Reimplement it clean-room: from public
  documentation and black-box behaviour only, without reading the incompatible source, and
  record what you consulted in a `CLEANROOM.md` next to the code.
- An incompatible implementation may be used as a test oracle only as a separate program,
  fetched or built at test time and never committed or shipped; its tests may be fetched at
  test time as expected results, never stored here.
- Anything copied from a compatible project (Apache-2.0, MIT, BSD, ISC, OFL for fonts) carries
  its licence and notices next to it and gets a row in `THIRD_PARTY.md`.
- Before adding a dependency that ships in a Worker, check its licence; copyleft is allowed
  only as development tooling that is never bundled.

## Git

- `node_modules/`, build output, `target*/`, Go module caches and third-party source
  checkouts are ignored; do not commit them (a harness that needs upstream source fetches
  it with a script). Lockfiles are committed. Before committing a new directory, check its
  size.
- Changes reach `main` through pull requests. Use `.github/pull_request_template.md`.
- One logical change per commit, with a message that says what changed and why.
