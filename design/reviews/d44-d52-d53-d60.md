## Findings by severity

### Blockers

None. No path was found that issues a token, a code or a grant key to anyone who does not hold
the credential that should be needed for it.

### Majors

#### M-1 (D44) The `Tenant` binding that viz-mcp now holds is an unscoped admin credential for every tenant — **reproduced**

`mcp/wrangler.jsonc` binds `Tenant` by `script_name: viz-control` so that it can call
`introspectAccessToken`. A Durable Object binding cannot be narrowed to one method, so viz-mcp can
also call `invoke`, `provision`, `serviceKey`, `notificationTarget`, `resolveKey` and
`recordUsage` on any tenant's object.

`Tenant.invoke(id, op, input)` trusts the `Identity` it is handed whenever `id.keyId` is absent.
Only control's own Worker is supposed to set it (`tenant.ts`, `invoke`).

Attack: any code path in viz-mcp calls
`stub.invoke({tenant: <any>, subject: 'key:nobody', kind: 'key', scopes: ['admin']}, 'keys.create', …)`.
Such a path could be a bug, a compromised dependency, or a future tool that reaches the binding.
viz-mcp is the internet-facing Worker that runs LLM-chosen tool calls on untrusted text. The call
mints an admin key in that tenant. The same forged identity can run `oauth.approve`, and
`approver()` in `ops-oauth.ts` treats any subject that does not start with `key:` as `live`
forever. A grant approved that way therefore never follows anyone.

From the same binding:

- `serviceKey` rotates the ruler's key with no overlap, which is a denial of service on rule
  evaluation;
- `notificationTarget` returns webhook secrets.

Test `R1` in `control/test/review-d44.test.ts`, both cases pass:

- a forged identity creates an admin key that works on `GET /whoami`, and the audit log names
  `key:nobody`;
- a forged `system:anything` identity approves a grant whose token introspects `active`.

D44 says "Nothing else is asked of it", and nothing enforces that. The gateway and the ruler held
this binding before this pull request; viz-mcp is the third holder, and the one that handles
untrusted input.

**Change:**

1. Export a named `WorkerEntrypoint` from viz-control (for example `OAuthIntrospection`) with the
   one method `introspectAccessToken`, checked against `props.caller` as in D45. viz-mcp binds that
   entrypoint instead of the class.
2. In `approver()`, fail closed: any subject that is not `key:` counts as `gone` until people can
   be checked. Otherwise sign-in (`kind: 'user'`) inherits this hole.

#### M-2 (D44) Unauthenticated, tenant-targeted load and billed writes on the tenant's control object — **reproduced**; partly known

`/oauth/token`, `/oauth/revoke` and the OAuth bearer path of `/mcp` route each request to the
Tenant object named in the presented credential (`vzc1|vza1|vzr1.<tenant>.<43>`), with no check
before the object. API keys are different: they are checked against KV first, so before D44 no
unauthenticated request reached a Tenant object.

Every tenant's whole control plane goes through that one object: every control API call, every
MCP request (introspection), and every token request.

The README's known risk says a forged credential "writes nothing". **That is false.**
`oauthToken` and `oauthRevoke` call `settle()` unconditionally, and `settle()` calls `schedule()`
twice, so each forged request runs `setAlarm` twice. Cloudflare bills each `setAlarm()` as a row
written.

Measured here:

| Test | Result |
|---|---|
| `R7` | 100 forged refresh and revoke requests: 200 `setAlarm` calls, 0 `deleteAlarm` calls |
| `R3` | A forged `/oauth/token` request: 1.52 ms (Worker plus object); a forged introspection: 0.65 ms (local workerd, sequential, 300 each) |

**Modelled:** one object serves somewhere between 300 and 1,500 such requests a second. At that
rate an attacker who knows only the tenant id can make the tenant's control plane and MCP
unavailable. The tenant id is printed in every code and token; it may also be guessable. Each
million forged requests costs the operator about $2 in row writes, plus Durable Object requests
($0.15 a million) and duration. The experiment that would settle the range is a spike with
clients as Durable Objects (AGENTS.md). It would measure a Tenant object's throughput on forged
`/oauth/token` and the latency of `whoami` under that load.

**Change:**

- **Before merging:**
  - call `settle()` only when the transaction changed something, and test it with a write counter;
  - correct the README's claim.
- **Before public exposure:**
  - make a forged credential refusable in the Worker without the object. One way is to put a MAC
    in the credential (for example the 43 characters as random ‖ truncated HMAC(deployment key,
    prefix ‖ tenant ‖ random)). Another is a KV negative cache.
  - add a rate limit (a Workers rate-limiting binding keyed by client IP and tenant) to
    `/oauth/token`, `/oauth/revoke` and failed OAuth bearers at `/mcp`.

### Minors

#### m-1 (D44) The expiry of an approver's key sets no alarm — **reproduced**

`oauthDeadlines` has no term for the expiry of the approver's key. `R6` used an approver key that
expires in 6 minutes. The alarm stayed set for 30 days later (2026-12-19), at the idle deadline.
Introspection refuses the grant correctly once the approver is gone. The grant key's KV record
stays valid at query, the ruler and control until the next sweep, up to 30 days. Only viz-mcp ever
holds that key, briefly, so exposure needs a leak.

**Change:** add the `expires_at` of approver keys to `oauthDeadlines`.

#### m-2 (D44) A body without `Content-Length` is read whole before its size is checked — **reproduced**

`readBytes` reads `req.arrayBuffer()` and only then compares the length. `R5`: a 4 MiB chunked body
to `/oauth/token` was pulled completely, then refused. The same applies to `/oauth/register`,
`/oauth/revoke`, and `stepUp`'s `req.clone().text()` in mcp. The memory used is bounded only by the
platform's body limit.

**Change:** read the stream with a byte cap.

#### m-3 (D44) Redirect URIs may carry bidi and format characters, shown raw — **reproduced**

`https://evil.example/cb/‮moc.elgoog` registers, and `/oauth/authorize` prints it unchanged
(`R4`). The "Returns to:" host line stays correct, `evil.example`, and IDN hosts show as punycode.

**Change:** refuse non-ASCII in redirect URIs, or display `new URL(u).href`.

#### m-4 (D44) A benign concurrent refresh ends the grant, and one answer is a 200 with dead tokens — **reproduced**; strictness known

`R2`: the same refresh token sent twice in flight returned 200 and 400, and the grant was revoked
with reason `refresh-reuse`. The 200's access token introspects `inactive`. The README documents
this strictness and RFC 9700 §4.14.2 permits it. The 200 is new information: the client
believes it holds tokens that are already dead.

#### m-5 (D44) Consent is not tied to the browser that started the flow — inspection

Anyone holding an authorize URL can ask an admin to run the `curl`, and the code then goes to that
client's registered https callback. The warning "approve only a connection you started yourself"
appears for loopback redirects only.

The page also tells the reader to run `curl … -H "Authorization: Bearer $VIZ_ADMIN_KEY"`. An agent
that has a person's admin key in its environment (kind `key`) can approve itself or an injected
client: the kind is a label, not proof that a person acted.

**Change:** show the warning for every redirect. A sign-in is the real fix (D44 "Would change if").

#### m-6 (D44) Scope hierarchy differs between control and mcp — inspection

Control treats `dashboards:apply` as including `dashboards:write`, which includes
`dashboards:read` (`routes.ts` `D_WRITE` and `D_READ`). mcp's `hasScopes` compares literally. A
token holding `dashboards:apply` without `dashboards:write` is therefore stepped up for
`dashboards:write`. MCP 2026-07-28, Step-Up Authorization Flow: "Servers **MUST** account for
scope hierarchies".

#### m-7 (D44) `localhost`, and registrations that do not name their issuer — inspection

- `localhost` is accepted as a loopback host; RFC 8252 §8.3 says it is NOT RECOMMENDED.
- The signed registration (`vzk1.<payload>.<mac>`) does not include the issuer. Two deployments
  that shared `OAUTH_CLIENT_KEY` would accept each other's client ids. D53 generates a key per
  Worker, so this is defence in depth only.

#### m-8 (D52) The real entrypoint rejects without a refusal word in a case the contract calls `unavailable`, so the ruler falls back to Remote Write — **reproduced**

`writeRecorded` calls `refuseEarly` outside any `try`. When any shard in the isolate is marked hot
and the tenant's `pool:<tenant>` cannot be read, the rejection is the bare `shard pool map is
invalid`. A pool map of a newer version than this release reads, or a KV error, does the same.

Test `edge/test/review-d52.test.ts`: the real `RecordedSamples` through the `RULER_SINK`
self-binding answered exactly `shard pool map is invalid`. The same call with no hot shard
answered `unavailable: shard pool map is invalid`. To mark a shard hot, the scratch copy of
`route.ts` exported its `hot` map; nothing else in it was changed.

`ruler/src/recorded.ts` therefore treats an entrypoint that exists and decided as one "not
answering by its contract", and sends the same batches by Remote Write. D52's own alternative (b)
names the cost: a second write to an ingest that is already struggling. Platform failures of the
callee, such as CPU or memory exhaustion or a lost connection, also lack a refusal word. They take
the same path in exactly the overload case, and each of the 3 attempts of a tick costs one RPC
plus one Remote Write.

No double count follows: reads de-duplicate on `(series, timestamp)` (DESIGN.md; query/README).

**Change:**

- in `writeRecorded`, wrap `refuseEarly`, and map any unexpected error to `unavailable:`, so that
  only a missing entrypoint or a platform failure lacks a refusal word;
- consider falling back at most once per tick.

#### m-9 (D53) A rollback across the key's creation, followed by an upload that does not inherit the key, generates a new key silently — **reproduced against the fakes**

The fail-closed check counts as evidence only the Worker's secret list (the deployed version's)
and the serving versions.

Test `D53-1` in `deploy/test/review-d53.test.mjs`: the version that serves has no key, an older
uploaded version has it, and the new upload does not inherit it. The result was exit 0 with
`action: created`, a new value and no refusal. That invalidates every client id signed under the
old key. `D53-2` shows that with inheritance from the newest version the key is kept (held under
the fake's model).

Which of the two Cloudflare does is **not measured** (D53 "Cost" says so).

**Change:** also count the versions uploaded since the previous release record (or the newest N
versions) as evidence that the key exists.

#### m-10 (D53) With `WRANGLER_LOG_SANITIZE=false` in the deploy's environment, the key is written to wrangler's debug log on disk — **reproduced with the real wrangler 4.164.0**

`deploy/lib/wrangler.mjs` hands `process.env` through to wrangler. Wrangler 4.164.0 writes every
log level to `~/.config/.wrangler/logs/` (or `WRANGLER_LOG_PATH`) unless `WRANGLER_WRITE_LOGS` is
false. `versions secret put` sends a JSON `PATCH …/versions/latest`. Its `INIT:` debug line holds
the body, and it is redacted only while `WRANGLER_LOG_SANITIZE` is true, which is the default.

The run, against a local fake API (`scratchpad/rv-d44/wr/`):

| Setting | Key in the log file | Key on stdout or stderr |
|---|---|---|
| Sanitize on (default) | not present | not present |
| Sanitize off (`WRANGLER_LOG_SANITIZE=false`) | present, as `"text":"MARKER-…"` in the log file | not present |

`D53-4` confirms that the wrapper passes `WRANGLER_LOG_SANITIZE=false` through to the `put`.

D53 promises "never … in a file". That holds by default only.

**Change:** set `WRANGLER_LOG_SANITIZE=true` and `WRANGLER_WRITE_LOGS=false` in the child's
environment, at least for `versions secret put`.

#### m-11 (D53) Another run of the same release can upload between the "newest" check and the PATCH — **reproduced against the fakes**

In `D53-3`, a version carrying the same `VIZ_RELEASE` and a marker var appeared after
`listVersions`. The key was put on that version and it was promoted, with exit 0. The
`VIZ_RELEASE` check still stops a different release. CI runs are serialised by the
`deploy-production` concurrency group; a run from a laptop is not. Impact: on the release that
creates the key, two runs can each create a different key, and the second promotion invalidates
client ids registered in between.

**Change:** tag uploads with a value unique to the run and check that tag on the keyed version.

#### m-12 (D60) A missing version-2 block is not detected, and readers first freezes the format now — **reproduced**

`readV2` refuses a missing or incomplete head, but the head does not list its blocks. In the test,
one middle block row of a robust z rule was deleted. The rows still read with no error, and the
point count went from 596 to 536 (`review-d60.test.ts`, "a block row that is missing").

No path in this release loses a block: writes are in the tick's or the warm-up's transaction
(checked). The reader's "never guessed" is therefore narrower than it reads. Once this reader
ships, adding a block list to the format costs version 3.

**Change (recommended now):** put the live block numbers, or each series' block span, in the head,
and refuse rows that disagree with it.

#### m-13 (D60) Rollback below this release once the gate is on — documented, not new

Once `ANOMALY_STATE_WRITE` is 2, a rollback to a release without this reader leaves rules
`state_unreadable`, and `release.mjs rollback` does not refuse it: D46 records schema versions,
not format versions. D60 "Cost" and "Would change if" say so.

**Change:** carry format versions in the release record before the release that turns the gate on.

## What was attacked and held

### D44

- **PKCE.** Missing, malformed and `plain` challenges are refused at `/oauth/authorize`. The token
  endpoint always requires a verifier and computes only S256, so there is no downgrade path
  (RFC 9700 §2.1.1, §4.8.2). The handle is unsigned, and `decodeRequest` and `approve` re-check
  everything in it.
- **Code interception and injection.**
  - A code is bound to its client, its exact redirect URI, its resource and its PKCE challenge.
  - The first try spends the code, and a second use revokes the grant with its tokens and key,
    in KV too (RFC 9700 §4.2.4).
  - `iss` is in the callback (RFC 9207), and `authorization_response_iss_parameter_supported` is
    advertised.
- **Refresh tokens.**
  - Rotated on every use; reuse revokes the grant (RFC 9700 §2.2.2, §4.14.2).
  - A refresh token presented by another client revokes the grant.
  - A refresh may narrow the scope but never widen it.
- **Token theft and replay.** Tokens live 1 hour, and control checks each one on every `/mcp`
  request. Revocation therefore takes effect at once at `/mcp`. Downstream services follow KV
  within the documented lag.
- **Revocation races.**
  - `issue()` re-checks the grant after the asynchronous crypto.
  - `introspect()` re-reads the grant, the key and the token row after `await`.
  - `R2` shows that the outcome under a concurrent refresh is safe.
- **Redirect URIs.**
  - Matched exactly. A fragment, user info, whitespace, backslash, quotes and control characters
    are refused.
  - The server never redirects by itself (RFC 9700 §4.11.2).
  - Loopback variants normalise as checked with the URL parser: `127.1`, `0x7f000001`,
    `2130706433` and `[0:…:1]` become loopback; `localhost.`, `localhost.evil.com`,
    `127.0.0.1.nip.io` and `[::ffff:127.0.0.1]` are refused.
  - A percent-encoded host (`good.com%2eevil.com`) is shown parsed, as `good.com.evil.com`.
  - A Cyrillic homograph is shown as punycode on the host line.
- **Registration forgery.** The HMAC is checked with `crypto.subtle.verify`, and the payload is
  re-validated after the MAC.
- **Rotation of `OAUTH_CLIENT_KEY`.** Bound clients keep refreshing, because the token endpoint
  compares the stored client id. New authorizations re-register. This is documented.
- **Scope escalation.**
  - No API changes a key's scopes. Keys are created, disabled, enabled, rotated and deleted, so an
    approver key cannot be "narrowed".
  - `admin` stands only for the dashboards scopes. `admin`, `write` and `monitors:write|ack` are
    never grantable.
  - Agent keys cannot approve.
  - A disabled approver suspends the grant, and a deleted or expired approver ends it at
    introspection.
- **Tenant confusion.** The tenant comes from the credential only; the hash covers the whole
  credential, tenant included. Editing the tenant matches nothing. A name nobody provisioned
  creates no storage. Introspection checks that `r.tenant === presented.tenant`.
- **`resource` confusion.** Audience is `<PUBLIC_URL>/mcp`, from configuration, never from `Host`.
  It is checked at approve, at the token endpoint when present, and at every introspection. A
  stage deployment has its own Tenant namespace. In `canonicalResource`, `\`, single-slash and
  dot-segment tricks all canonicalise to something other than the real resource.
- **Introspection leaks.** Introspection is RPC only; there is no RFC 7662 endpoint. Inactive
  reasons reach only the token's holder. The grant key is never returned to a client and never
  logged (their test, and reading).
- **Timing.**
  - Lookups are by SHA-256 of a 256-bit credential.
  - `sameString` compares equal-length public strings.
  - The HMAC check is constant-time (WebCrypto).
- **Consent CSRF and clickjacking.**
  - Approve is a JSON `POST` authenticated by a header, with CORS limited to the app's origin.
  - `/oauth/authorize` has no side effects and answers `text/plain`.
  - The page sends `nosniff`, `frame-ancestors 'none'`, `X-Frame-Options: DENY` and
    `no-referrer` (RFC 9700 §4.16).
  - The `curl` line embeds only the base64url handle and the issuer, so it cannot inject shell.
- **Error messages and logs.**
  - No error carries a credential.
  - The catch-all logs only the error's class.
  - The `vza1` token is never passed downstream (MCP "Token Passthrough").
- **Storage dump.**
  - Codes and tokens are stored as SHA-256.
  - The grant key's secret is sealed with AES-GCM under HKDF of each credential, with tenant and
    grant as associated data.
  - `key_secrets` holds the SHA-256 of a secret of about 238 bits.
  - A dump yields nothing usable.
- **DoS on `/oauth/register`.** Registration is stateless (HMAC only) and capped at 8 KiB (but see
  m-2).

### D52

- **Tenant spoofing.** Only a holder of a binding whose `props.caller` is `viz-ruler` gets past
  `unauthorized`. The tenant passes `TENANT_ID`, and every batch id must start with `<tenant>/`.
  The ruler supplies its own object's tenant. `props` is asserted by the caller's own config, so
  the trust boundary is everyone who can deploy a Worker to the account. That is the same boundary
  as binding viz-ingest's `Shard` class by `script_name`; D45 records it.
- **Reach from outside.**
  - `RecordedSamples` is a named export, and the default `fetch` never routes to it.
  - The gateway binds the default entrypoint.
  - Production viz-ingest is built from `stack/wrangler.jsonc`, which has no self-binding.
  - `edge/wrangler.jsonc`'s three self-bindings are used by its tests only, and `viz-edge` is an
    alias of viz-ingest, never deployed under its own config.
- **A real refusal never goes by Remote Write.** Refusal words survive the binding (local workerd,
  the edge suite and `review-d52`). `series_limit`, `invalid` and `unauthorized` are reported at
  once.
- **Timeouts do not trigger the fallback.** The group timeout races outside the sink.
- **Idempotence after a crash or a fallback.** Re-sending is harmless because reads de-duplicate on
  `(series, timestamp)`. Crash replay is covered by `ruler/test/recorded.test.ts` against the fake
  entrypoint.

### D53

- **Leaks.**
  - The value goes on stdin, not argv.
  - It is not in the environment.
  - The `put`'s output is `quiet` and scrubbed, as are error messages.
  - The release record holds names only. The PR's own tests check this through a real child
    process.
  - Exception: m-10.
- **Cross-release patching.** The `VIZ_RELEASE` check on the keyed version catches it.
- **A key set now but missing from the upload.** Refused with exit 3 (their test).
- **Concurrent CI deploys.** Serialised by the workflow's concurrency group.
- **Rollback with inheritance from the newest version.** The key is kept (`D53-2`).
- **What `versions secret put` does.** Read in wrangler 4.164.0's source: it is a server-side merge
  `PATCH` of `versions/latest` that deploys nothing, as D53 assumes.

### D60

- **This release never writes version 2.**
  - Every writer takes `anomalyStateWrite()`: tick, warm-up, shard-move export, import.
  - Production returns the constant 1.
  - `TEST_ANOMALY_STATE_WRITE` is read by the harness only.
  - Mutant `ANOMALY_STATE_WRITE = 2` in a scratch copy: 4 tests failed in `anomalystore.test.ts`
    and `anomaly.test.ts`, so it was caught. The source was restored and diffed against the
    worktree: identical.
- **Equal scores against a version 1 reference.** The run covered:
  - a query offset that changed during incremental writes (points off the grid);
  - gaps across every series;
  - a series pruned and returning;
  - the gate going 2 → 1 → 2, restarting from rows at each change;
  - random evictions.

  It ran 1,600 ticks for each of robust z at 200 points, robust z with a 37-minute window, and
  seasonal hourly ×2 (MAD). Result: **0 mismatching ticks, and the same final state** (with the
  harness's own `Table`).
- **Changing the group's interval** deletes the state (`sameStep`), so blocks are never decoded
  with another step.
- **Eviction mid-write.** Tick and warm-up writes are in one `transactionSync`, so they are atomic.
- **Shard move.** A bundle's version 2 rows are read by what they say and rewritten whole. Rows of
  both versions together, or malformed version 2 rows, are refused and kept.

Each `setAlarm` is billed as a row written (Cloudflare's Durable Objects pricing, read by the
review), so before, every forged token or revocation request cost two billed writes and a request
to the tenant's object, whose one thread also serves that tenant's whole control plane; after, it
costs the Worker one HMAC. In local workerd the service-binding hop costs more than the object call
it replaced for a made-up token (0.58–0.89 against 0.41–0.55 ms), and for a **live** token, measured
the same way in a scratch copy (300 calls, 3 rounds), introspection through the binding took
1.76–2.42 ms against 0.90–1.62 ms on the object directly: the price of the narrow entrypoint is
one hop per `/mcp` request, about 0.6–0.9 ms here. Not measured on Cloudflare (a spike with clients
as Durable Objects, AGENTS.md, would; review M-2's modelled throughput is unchanged as a model).
The machine's load average was about 10 during these runs.
