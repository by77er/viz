## Summary

**One blocker, in D55.** A tenant whose two tables' publisher cursors diverge can lose changes
from the published table without any error. It needs one table with no cursor (or a cursor in an
older incarnation) and the other table with a cursor below the newest checkpoint. The publisher
then re-bases the tenant from that checkpoint, but plans the second table "from its cursor" over
changes that start *after* the checkpoint. The changes between the cursor and the checkpoint are
skipped and the cursor moves past them. The publish reports `ok`, and only the off-path `verify`
notices. This is reproduced for format 1 and format 2 checkpoints. A one-line fix passes the
reproduction and the whole publisher suite.

**Two majors, in what the PR does with the state limit.**
- P-2: lifting the 16 MiB production pin in the same release makes a rollback, or a gradual
  deployment, stop ingest. The release before refuses every unit with `full` for any tenant above
  16 MiB, and its drain builds the whole state in memory at its next checkpoint. Nothing in the
  release record says so.
- P-3: at 300 MiB, a ledger rebuild (20 s here) and a publisher first publication (27–38 s here)
  are close to the unconfigured 30 s CPU default. Neither keeps progress, so a reset starts it
  again. This is modelled only; nothing was measured on Cloudflare.

**D47's mechanism held up.** I found no interleaving in which a part differs from the state at
its version. That includes mutations committed while a part's PUT is in flight, followed by a
failed PUT, a lost answer, or success. The existing suite does not exercise that case: a mutant
that drops pre-images during an in-flight PUT survives all 13 checkpoint tests. I wrote the test
that kills it (P-4).

**D48's filter matched an independent reference** on 60,000 random batches and filters. It found
no page boundary that splits or repeats a batch, and no cursor that survives a change of stream.

## Blocker

### P-1. A table whose cursor is below the newest checkpoint skips the changes in between, and the publish says `ok` (D55)

**What happens.** `attemptStaged` reads each tenant's log once, from the lowest cursor of its two
tables. If any table has no cursor, it reads from `null` (`publisher.ts:727`). If the lowest
cursor is in an older incarnation, `readTenantLog` treats it as `null` too (`log.ts`,
`readTenantLog`). Either way the tenant is re-based from the newest checkpoint at version `C`,
and `log.changes` starts at `C + 1`. `plan()` then decides per table:
`rebase = !cursor || cursor.ledgerIncarnation < log.incarnation` (`:801`). A table whose cursor
is in the newest incarnation at version `X < C` is therefore planned by `planFromCursor`. That
function walks `log.changes`, skips versions `<= X` (`:844`) and never checks that the log starts
at or below its cursor. Versions `X+1 … C` are not in `log.changes`, so they are silently
skipped. The table's cursor then moves to the head.

Before D55 a re-base always started from the incarnation's base. Every cursor in that
incarnation is at or above the base, so the missing check did not matter. Reading checkpoints
broke that invariant. Format 1 checkpoints, which the release before already writes in
production, trigger this as well as format 2.

**Interleaving (reproduced).**
1. A new tenant. Units 1–3 are logged.
2. Publish. `metric_samples` commits, with its cursor at the head, version 4 (the stream's
   registration is version 1, units 1–3 are versions 2–4). The
   `metric_series` commit fails after writing its manifests (`failAt('manifests-written',
   'metric_series')`). Any failure between the two tables' commits does the same: an eviction,
   a CPU-limit reset, an R2 error, or a `plan.problems` entry for one table only.
3. The ledger admits units 4–6 (versions 5–7), writing a format-2 (or format-1) checkpoint at
   version 7, then unit 7 (version 8).
4. Publish. `metric_series` has no cursor, so the tenant is re-based from the checkpoint at 7.
   `metric_samples` is planned from its cursor over changes 8 onwards.

The result was the same for a format 2 and a format 1 checkpoint. The tenant report is
`status: "ok"`, with both cursors at version 8. In `metric_samples`, the ledger has 7 live files
and Iceberg has 4. The samples files of units 4, 5 and 6 are missing, for good.
`verify('metric_samples')` reports them in `missingFromIceberg`, but nothing on the publish path
looks.

A removal in the skipped window would leave a file published that the ledger removed: expired
data stays visible, or a compaction's inputs stay without its output. A later removal of a file
added in the window makes the table `inconsistent` (stuck). An addition in the window that is
never removed is lost from the publication silently.

**How likely.** Each trigger alone is uncommon. The combination becomes likely for exactly the
large tenants D55 is for. A first publication of 300,000 files took 27–38 s here (P-3). A reset
during the second table's commit leaves the first table with a cursor and the second with none.
After that, every publish re-bases the tenant. The first table loses the changes between its
cursor and the next checkpoint the ledger writes, and the ledger writes one every few hours for
a busy tenant. The same happens when one table alone has a persistent `plan.problems` entry: the
skip then recurs at every checkpoint.

**Fix (tried).** In `plan()`:
`const rebase = !cursor || cursor.ledgerIncarnation < log.incarnation || (log.base !== null && cursor.version < log.start)`.
`stage` holds the whole state at `log.start` plus the changes read, so the staged diff against
`live` is correct for any cursor. With this change the reproduction passes, and the whole
publisher suite passes: 101 of 101, the 99 tests of the PR and the 2 of this review,
`npx vitest run --maxWorkers=2`. `planFromCursor` should also refuse a log that starts above
its cursor (`log.start > cursor.version`) instead of assuming it does not, so that a later change
cannot reintroduce the skip.

The test: `rv-d47/publisher/test/review-skip.test.ts` in the scratch directory (see "Tests
written"). It fails on the PR (2 of 2) and passes with the fix.

## Majors

### P-2. A rollback, or a gradual deployment, across the pin removal stops ingest for every tenant above 16 MiB, and the release does not say so (D47, D55)

This PR removes `LEDGER_STATE_MAX_BYTES` from `stack/wrangler.jsonc`, so tenants may grow to
300 MiB. The schema change (migration 3) is additive, so the release record calls the release
before a safe rollback target. That release is frozen in `ledger/bench/before/`, the code the
authors use as "ledger N−1". On storage this release wrote, for a tenant above 16 MiB:

- **Every `addUnit` answers `full`** (`before/ledger.ts:192`, `:725–731`): it compares the same
  `meta.state_bytes` with its own 16 MiB default, and the rolled-back version also restores the
  16 MiB pin. Ingest for that tenant stops: flush retries, the shards fill, and senders get 429.
  `replace` and `expire` still pass, but they cannot bring a 300 MiB tenant back under 16 MiB.
- **Its drain builds the whole state in memory at its next checkpoint**
  (`before/ledger.ts:1079–1087`: `stateFromSqlite()` and `JSON.stringify`, in the synchronous
  step that fixes the segment's bounds, before the segment's PUT). Its trigger,
  `log_bytes_since_ckpt + body >= ckpt_bytes`, carries over from this release's meta, so it can
  fire at any point in the rollback window. At 300 MiB the authors extrapolate about 1.2 GB for
  that step (`ledger/README.md`, "Not measured"), and the isolate allows 128 MB. Each retry
  reaches the same step, so the log stops. Shards keep their rows, so nothing is lost, but
  nothing is logged either. An out-of-memory reset may also reset other objects that share the
  isolate (training knowledge, not checked).
- **The publisher of the release before** reads a new incarnation's base whole. A re-base of a
  tenant above 16 MiB in the rollback window runs out of memory. A publish covers every pending
  tenant, so the whole publish fails.

`contracts/LEDGER-LOG.md:225–230` and `ledger/README.md:413` mention only the rebuild after a
storage loss ("stuck, not lost"). COMPATIBILITY §6 asks that the rollback target "reads every
format version any release since T has written". In practice the release before cannot read a
base or checkpoint above 16 MiB, so for those tenants this release is forward-only. `deploy/`
would not refuse the rollback.

**What would close it.** Ship the code with the 16 MiB pin kept, and lift the pin in a later
release once this one is the rollback floor. A rollback then lands on code that can checkpoint,
rebuild and re-base large states, so nothing runs out of memory. A rollback below the lifting
release still answers `full` to tenants above 16 MiB. That needs to be in the release record:
either mark the lifting release forward-only (§6), or have the record carry the state limit and
make the rollback check compare it. Not reproduced. It follows from the frozen code at the lines
cited.

### P-3. The 300 MiB limit goes to production before its CPU cost is known, and nothing keeps progress (D47, D55)

Measured here, in local workerd:
- a ledger rebuild of 300,000 files took 20.3 s (`ledger/README.md`);
- a publisher re-base took 8–17 s, and a first publication took 27–38 s (D55, "Measured").

Durable Objects allow 30 s of CPU per invocation by default (D51). Neither `stack/wrangler.jsonc`
nor `publisher/wrangler.jsonc` sets `limits.cpu_ms`. Wall time here is not CPU time on
Cloudflare. Modelled CPU per invocation:

| Work | Modelled CPU |
|---|---|
| Rebuild | 10–40 s |
| First publication | 15–45 s |

Two experiments would settle these ranges:
- S4's ledger at 300,000 files on Cloudflare: a storage loss and rebuild, with CPU time read from
  the analytics API;
- the publisher's first publication of the same tenant.

The consequence is what makes this major. Neither job keeps progress (`ledger/README.md`, "Not
implemented"; D55 "Would change if"), so a reset restarts it from the beginning:
- **ledger:** a tenant whose rebuild exceeds the budget is refused for good after a storage
  loss;
- **publisher:** a re-base or first publication that exceeds it resets the whole publish, so
  every tenant pending in that cell stops being published.

A reset between the two tables' commits is also P-1's trigger. The design names the condition
("would change if … exceeds the CPU limit"). It still lifts the pin before measuring it.

**What would close it.** Keep a pin at the largest size measured on Cloudflare within the
budget, or set `limits.cpu_ms` and measure, before the pin goes.

## Minors

### P-4. The pre-image rule is never tested with a mutation while a part's PUT is in flight (D47)

`checkpoint.test.ts`'s property test mutates only between parts (`step(l, 0, 1)` returns, then
`mutate`). The interesting window is between building a part and recording its cursor. There,
the part's own keys must still leave pre-images, because a failed PUT rebuilds the same part.
I wrote `rv-d47/ledger/test/review-inflight.test.ts`. It pauses the n-th part PUT inside the
object (n = 1, 2, 3). While the PUT is paused it commits three mutations:
- a `replace` that removes a samples file the in-flight part holds and adds a key that sorts
  inside the part's range;
- an `addUnit`;
- an `expire` of day 0.

The PUT then fails, has its answer lost after the write, or succeeds. The test lets the
checkpoint finish and requires two things: the parts hold exactly the files at the checkpoint's
version, and a rebuild from it equals the live ledger.

- **PR code:** 9 of 9 pass. The mechanism is right.
- **Mutant** "no pre-images while a part PUT is in flight" (an in-memory busy flag that makes
  `tracking()` return false around the PUT): 9 of 9 of the new tests fail, and all 13 tests of
  `checkpoint.test.ts` pass. **The mutant survives the existing suite.**

Recommend adopting the test.

### P-5. A format-2 checkpoint's tombstones are read when the part is built, not at its version (D47)

Pre-images cover `file` only. The tombstone phase reads `tombstone WHERE version <= V`
(`ledger.ts:1425`) as of when the part is built. Two things change that table in the meantime
without leaving a pre-image:
- `forget(keys)`, the janitor, deletes tombstone rows without a version (`:1045–1058`);
- `bury` uses `INSERT OR REPLACE` (`:600`), so a key removed at or below V, re-admitted, and
  removed again moves above V. This needs a caller bug.

So a checkpoint can lack tombstones that existed at V. Today this is harmless: a forgotten
tombstone's object has already been deleted with the publisher's consent. But the contract and
the property test claim "exactly the state at its version", tombstones included. The test passes
only because no janitor runs during it. Either say in LEDGER-LOG.md that tombstones are "as of
when the part was written", or record a pre-image in `forget` while a checkpoint runs.

### P-6. Parts of a checkpoint in progress are never deleted once the incarnation changes (D47)

`startIncarnation` deletes the `ckpt` row (`:1841`). `deleteSuperseded` sweeps only the current
incarnation's prefix (`:1523–1539`). A storage loss or a `restartFromSqlite` in the middle of a
checkpoint therefore leaves up to the whole state, about 300 MB, in the old incarnation's prefix,
for good. LEDGER-LOG.md's "Truncation" section does not mention it. Sweep `ckpt-*-*/` of older
incarnations once a newer incarnation's first checkpoint is complete, or list it under "Not
implemented".

### P-7. A rebuild passes over the newest checkpoint on any error, including a transient R2 read failure (D47)

`replaySegments` catches every exception from `loadCheckpoint` (`:2087–2096`) and moves on to an
older checkpoint or the base. At 300 MiB, a single failed GET of one part turns a rebuild from
parts into a rebuild from the 250 MB base line, the slow path, while the tenant is refused. A
contract violation (`LogFault`) should pass over. A failed R2 read should retry the start, which
the start's 5 s retry already does.

Separately, after a failure the three parts read ahead keep their connections while the base's
GET starts. That briefly exceeds six in flight. The runtime queues the excess rather than
failing (training knowledge), so this is not a correctness issue.

### P-8. The publisher stops a tenant on a corrupt checkpoint that the ledger's own rebuild passes over (D55)

`readNewestCheckpoint` returns `corrupt` (`log.ts:605–627`), and the tenant waits until the
ledger writes a newer checkpoint. For a 300 MiB tenant that is at least the log volume of one
state, hours. D55 records this as alternative (e) and as "would change if". The asymmetry is
deliberate. What is missing is any signal: no status besides the tenant report, and no alert.
At minimum, surface `corrupt` and `incomplete` re-bases in the publisher's status. `incomplete`
can recur if checkpoints complete faster than a re-base reads one; that is unlikely at the
current cadence.

### P-9. D48's contract does not say what a paged reader does when an older shard answers mid-read (D48)

`TailResult`'s comment says an `ok` without `page` comes from an older shard and holds "the
whole tail, unfiltered and unpaged". A reader that sent a `cursor` for page k and gets such an
answer, because of a rollback or a gradual deployment between its pages, must discard pages
1…k−1. If it appends instead, every row is counted twice against the query's fetch and sample
budgets. The engine de-duplicates by `(series_id, ts)`, so results are not wrong. Write the rule
down where the caller (D54, not in this PR) will read it. Also: a v1 shard ignores filter fields
it does not know (COMPATIBILITY §3.2) and still returns `page`, so any new filter field must
come with `v: 2`. Today that yields only a superset, which is safe because the engine applies
the matchers again.

### P-10. A shard has no bound on the memory of concurrent paged reads (D48)

A page holds up to `TAIL_PAGE_MAX_BYTES` (16 MiB) of payload until the RPC result is
serialized. `tailPage` is synchronous, but answers from concurrent reads (eight split leaves per
query, several queries) can be alive at once. Before D48 the whole unpaged tail was returned, so
this is an improvement. Still, the default `maxBytes` is an eighth of the isolate per read.
Consider a smaller default (the measured selective read was 0.7 MB) or a per-shard budget
across reads in flight.

## Nits

- **N-1 (D47).** When a format-2 checkpoint completes, `segs_since_ckpt` and
  `log_bytes_since_ckpt` are reset to 0 (`ledger.ts:1483–1484`). The segments written after V
  while the parts were being written are forgotten, so the next checkpoint comes later than the
  policy says. The cost bound still holds.
- **N-2 (D47).** Part budgets count UTF-16 code units (`line.length`, `:1388`). The contract
  says "1 MiB" of bytes, so a part of non-ASCII keys or fragments can be up to three times
  larger.
- **N-3 (D55).** The manifest's `bytes` is "informational" in `contracts/ledger.ts:392`, but the
  publisher refuses a mismatch as `corrupt` (`log.ts:741`). One of the two should change.
- **N-4 (D48).** The cursor's filter binding sorts label pairs with the default `sort()`, which
  compares the arrays as `"name,value"` strings (`tail.ts:128`). If names or values contain
  commas, two orders of the same filter give different canonical texts, and a valid cursor is
  refused as `invalid`. It fails closed.
- **N-5 (D47).** The `drain()` admin RPC passes unbounded part counts, so one call writes a
  whole checkpoint: 272 PUTs at 300 MiB, about 46–109 s modelled. No production caller uses it.

## What was attacked and held

- **Parts that mix versions.** Mutations ahead of and behind the cursor are covered by the
  authors' tests. A mutation during an in-flight PUT, followed by a failed PUT, a lost answer or
  success, held in 9 of 9 cases of the new test. Eviction between a part's PUT and its cursor
  update rebuilds the same bytes from the same cursor (the `parts = ?` guard). A release without
  tracking is abandoned through `tracked`. Read in full: `record`, `preimageOf*`, `buildPart`,
  `checkpointStep`.
- **A crash between the manifest and the deletion.** The manifest is retried with identical
  bytes (`at`, the totals and the streams come from SQLite). The deletion is left for the next
  checkpoint. Manifests are deleted before parts. The authors' crash test covers every await
  and passes.
- **A rebuild or re-base that reads a manifest whose parts are being deleted.** The ledger's
  rebuild meets a missing part as `LogFault` and passes over to an older checkpoint or the base.
  The publisher returns `incomplete`, publishes nothing and lists again. A reader can never
  combine parts of two attempts: every part header names its attempt, and the decoders check
  it.
- **Reading a checkpoint of an incarnation that is not the newest.** Both readers take the
  newest incarnation and filter manifests by it. A newer incarnation that appears during a read
  is picked up by the next publish, which replaces the state rather than extending it (S-8).
- **Pre-images lost or applied twice.** Each pre-image is written in the mutating transaction.
  `INSERT OR IGNORE` keeps the first, which is the state at V. Pre-images are cleared at begin,
  at abandonment, at completion and at a new incarnation.
- **Tail page boundaries and cursors.** The next page resumes at the first batch that was not
  returned, so no batch is split or repeated. The cursor is bound to tenant, stream incarnation,
  watermark and filter. Every page re-checks the stream and the discard fence: a seal or flush
  changes neither, a discard above the watermark answers `stale_watermark`, and a lost or
  recreated stream answers `incarnation_mismatch`. The scan budget always makes progress.
- **The filter skipping a matching row.** `shard-filter-prop.mts`, my own VZB1 encoder and
  reference, compared 3 seeds × 20,000 random batches and filters with no mismatch:
  - series ids at both signs and the edges of the key space;
  - time bounds at and around the edges;
  - absent-label matching, non-ASCII and comma-bearing values, and metric sets;
  - `splitKeyRange` partitions 2^64 exactly as `part_of` does.

  It has teeth: three mutants (key read as signed, `minTs` exclusive, an empty wanted value
  ignored) were each caught at once.
- **Release skew covered by the authors' tests.**
  - Ledger N−1 rebuilds from this release's log, passing over format 2.
  - This release reads format 1.
  - The publisher reads ledger N−1's log, format 1 checkpoints included (`LedgerBefore` in its
    tests).
  - Shard N with query N−1: the call without options takes the old path unchanged
    (`shard.ts:857`).
  - Publisher N−1 reads no checkpoint.
  - The exceptions are P-2 and P-9.
- **R2 consistency.** The design relies on strong read-after-write and list-after-write
  (documented by Cloudflare: training knowledge, not checked here) and on an atomic
  `If-None-Match`. Under weaker listings it still fails closed:
  - a missed newer manifest means an older checkpoint plus segments, which is correct;
  - a deleted manifest still listed means `incomplete`;
  - a part not yet visible behind a visible manifest means `incomplete`, then a retry.
- **Six connections.**
  - Ledger: parts are written one at a time, at most four parts are read ahead, and at most six
    segments are read during a replay. The one exception is in P-7.
  - Publisher: `Slots(6)` covers every R2 operation of a publish, a GET until its body is read.
    The authors' test asserts at most six. I found no path that holds a slot while waiting for
    another.
  - Shard: no R2 on the read path.
- **128 MB.**
  - Ledger: one part (about 1 MiB) is built in one step, a format-1 object only up to the
    one-part estimate, a rebuild holds 256 rows and up to 8 MiB of segments, and the base is
    written in 256 K pieces.
  - Publisher: a window of four parts, files in SQLite, and the authors' runs under a 32 MB heap
    cap.
  - Shard: up to 16 MiB per page (P-10).
  - Not covered: `verify` and the release before (P-2).
- **The protocol model.** `spec/README.md` L7 says checkpoints are not modelled, so no bounded
  check of D47 was possible. I ran none. P-4's test is the substitute.

## Verdicts

- **D47 (ledger checkpoints in parts): approve with changes.** The protocol is sound as built.
  Required before merge: P-2 (keep the pin for one release, and record what a rollback does) and
  P-3 (no production limit above what is measured within the CPU budget on Cloudflare).
  Recommended: adopt P-4's test; P-5, P-6 and P-7.
- **D48 (filtered, paged tail reads): approve.** No defect found in filtering, paging or
  cursors. P-9 and P-10 are for the contract text and the caller (D54) to settle.
- **D55 (publisher re-base from checkpoints): reject until P-1 is fixed.** The fix is one line,
  with a test that fails before and passes after. Required with it: the contiguity guard in
  `planFromCursor`, and P-2 and P-3, which concern the same pin removal. Recommended: P-8.
