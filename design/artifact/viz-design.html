viz: an observability store that lives in one Cloudflare account

Metrics in Parquet on R2, published as Iceberg tables, with PromQL on top; TraceQL and LogQL engines built and on main, their storage still proposed there. Monitors and dashboards that agents and people share. This page is the architecture as built on main, what the development branch adds beyond it, what has been measured and how, what reviews and a protocol model changed, and what is still open.

Read this first

On main: the write path, the query service, the ruler and notifier, the control plane, the MCP server with API keys and thirteen tools, the gateway and the PromQL engine (pull request #1); the clean-room TraceQL and LogQL engines (#2), with the Go-regex translator they share (#4); the ruler's SLO rules, warm-ups, backtests and CPU budgets (#3); and the write path's completion (#5): series-level pruning, the shard's paged tail reads, ledger checkpoints in parts, the RecordedSamples entrypoint, release records with schema versions, and the Iceberg publisher deployed, bound to ingest and gating deletes. On the development branch only: the query service's use of the paged tail, OAuth for MCP clients, a fourteenth agent tool (backtest_monitor), the ruler writing through RecordedSamples and new anomaly defaults, the first stage of spans and logs storage, registration before writes (being built after its review), and the web app with design system v8 (in review).

The first production deploy is pending a repository secret, so nothing serves vis.bitcru.sh yet. Staged copies ran on Cloudflare on 18 and 19 November, three times, and were deleted afterwards (deploy/README.md).

Three things are not done on main. Spans and logs storage is proposed, not built; its first stage is on the development branch. Production keeps the ledger's state at 16 MiB for this release. Memory no longer bounds it in the ledger or the publisher, which reach 300 MiB locally, but the release before cannot hold a larger state, and a rebuild or re-base above 16 MiB has not been timed on Cloudflare against the CPU limit. The query service does not read the shard's paged tail, so every query still reads every shard's whole tail; the development branch reads it filtered and paged (D54).

Every number below says what kind it is: measured on Cloudflare (with date and runs), measured here on a shared development machine, or modelled. Costs and most latency targets are still models.

The shape

For each tenant, one small ledger says which files exist. Everything else follows it.

LedgerOne Durable Object per tenant lists the live files of all that tenant's tables, plus a watermark per shard stream. It answers at its SQLite commit and writes its change log to R2 in batched segments, so it can be rebuilt from R2 alone.
TailRows that were acknowledged but are not yet in a listed file are held by exactly one shard, in a write-ahead log. Shards discard only what the ledger's R2 log already holds.
SeamA query reads one ledger version, then asks each shard only for rows above its watermark. A shard that has already discarded those rows refuses, and the query re-reads the ledger. No silent gaps.
PublicationIceberg snapshots are produced from the ledgers' logs every few minutes, for external engines. viz's own queries never wait on the catalog. Read back by two engines; wired into ingest, which nudges it, and physical deletes wait for it.

The parts, as built

Write path

edge authenticates the key and decodes Remote Write 1.0 or OTLP metrics into columnar batches, routed by sender. A shard with 64 appends in flight or 16 MB pending refuses at once, before reading anything, with 503 and Retry-After; accepted appends share one SQLite transaction and each caller is answered after it (D37). A seal reaches flush through a queue, with a KV marker and an hourly sweep under it (D18). The ledger admits each flush unit in one transaction, answers, and drains its changes to R2 as one segment about 0.2 s later; shards discard only what is logged (D36). A checkpoint of a state over 1 MiB is written in parts across drains and a rebuild streams into SQLite, so no step holds the whole state (D47). viz-ingest also exports RecordedSamples, an entrypoint for the ruler's recorded samples whose service binding is the credential (D45). On the development branch edge also decodes OTLP traces, OTLP logs and Loki push behind a flag, into shards of their own; nothing flushes them yet (D57, D58). DESIGN §4

Storage and maintenance

Tenant-pure Parquet files for metric samples and series. A per-tenant maintenance run expires whole days (30 by default), merges files in a Worker (at most 16 MB per step, 70 MB of WASM memory measured), and deletes what the ledger calls deletable once the cell's publisher has released it too. A merge never deletes its outputs; each output records its inputs, and the sweep deletes an unlisted output only once an input is gone for good, with no clock involved (D30). An idle deployment wakes no object. DESIGN §5.2

Read path

One ledger read gives a version, its files and its watermarks; shards return rows above them or refuse. Files are read through leaf Durable Objects, each with its own six connections (D17). Aggregations split over leaves that each own a range of series keys and return exact partials, byte-identical to one place (D31). /api/v1/plan reports what a query would read without reading it. Series-level pruning reads only the row groups that hold a selected series (D41), and the shard can filter its tail by time, metric, label and key range and answer in pages (D48). On main the query service does not ask for that, so it still reads every shard's whole tail; on the development branch it reads the tail filtered and paged (D54), counts the label endpoints over leaves (D56) and gives split parts their id range of the series files (D59). query/README.md

Engines

A Rust core with no I/O, compiled to WASM: Parquet encode and decode, PromQL, split execution and the cardinality report. The TraceQL and LogQL engines, merged through pull request #2, are clean-room crates checked against Tempo and Loki run as black boxes. TraceQL has a hand-written parser that refuses nesting deeper than 100 levels, and follows Tempo's evaluator where the documentation is silent, never its storage shortcuts (D40). LogQL runs its vector operations on the PromQL evaluator (D49) and follows Loki's observed behaviour where the documentation is silent (D50). Since pull request #4 both compile regexes in Go's dialect, as Tempo and Loki do, through one shared translator, engine/goregex. Both wait for spans and logs storage, which is proposed on main and in its first stage on the development branch. engine/

Monitors

Ruler objects evaluate each group per tick through the query service's HTTP API with a service key that the tenant's control plane issues, one call in flight per object (D39). Anomaly rules default to EWMA, or a static threshold for pages (D33); on the development branch, rules that do not page default to the robust z-score with a quantile spread instead (D33, rewritten). Since pull request #3, SLO rules raise the SRE Workbook's multi-window burn-rate alerts from one query per rule per tick (D42); new anomaly and SLO rules are warmed from history in memory-sized windows under budgets checked before anything is fetched, and backtests replay the same evaluation (D43); both are priced in CPU and refused whole over budget, never cut off by the platform (D51). Recorded samples go back through Remote Write; viz-ingest exports RecordedSamples for them (D45), and on the development branch the ruler writes through it over a service binding, with Remote Write as a fallback for one release (D52). ruler/README.md

Delivery

One Notifier per tenant groups, inhibits and silences with Alertmanager's semantics and sends from a transactional outbox. Each body is built once and every attempt sends the same bytes under the same Idempotency-Key, signed with HMAC-SHA256. The destination (a webhook URL, viz's viz.notification/v1 or Alertmanager's JSON, a write-only secret) is set in control and offered as the receiver viz:default. A dead-man's-switch alert is built in. D39

Agents and control

control keeps keys, dashboards and their revisions, proposals, settings and an audit log in one Tenant object per tenant. mcp is a stateless MCP server with 13 tools on main, served also as JSON under /api/v1/agent through one dispatcher (D25–D27). The development branch adds a fourteenth, backtest_monitor: read-only, it reports when a monitor would have fired and resolved, under the ruler's budgets. Results fence tenant text as data and return usage counters (D28). Agents propose new dashboards and changes, and a person applies them (D29). The tenant comes only from the credential. On main that is an API key. On the development branch an MCP client may instead hold an OAuth access token from control, granted after a person approves it with an admin key and never broader than that key (D44); the deploy generates control's client-signing key once and replaces it only when told to (D53). OAuth has not run on Cloudflare. mcp/README.md

Publication

One publisher object per cell writes Iceberg v2 metadata straight to R2, applying each tenant's ledger log strictly in version order and stopping at a hole rather than skipping it (D34). viz-ingest binds it, every maintenance run nudges it, its own alarm publishes about two minutes later, and a removed file is deleted only once it releases it; Trial 3 ran this on Cloudflare. An idle cell has no alarm. It re-bases a tenant on a new ledger incarnation from its newest checkpoint (in parts) or its base, streaming into SQLite (D55): at 300,000 files it fits in about a third of the isolate's 128 MB, measured locally. A table whose cursor is below the checkpoint its tenant is read from is re-based with it, so no change in between is skipped: an adversarial review found that skip, and it is fixed. The managed catalog is undecided (S8). publisher/README.md

From a push to production

Every push to main deploys, so two releases always share storage for a while. Every Durable Object records a schema version and refuses storage newer than its code; formats that cross a release carry a version; readers deploy before writers (D24, UPGRADES.md).

  1. The checks of ci.yml run: both WASM engines built once, the Rust tests, and type checks and tests for each TypeScript component.
  2. deploy.sh ensures the bucket viz-lake, the KV namespace viz-config and four queues, and generates each Worker's configuration.
  3. release.mjs refuses a release whose Durable Object migrations no commit acknowledges, uploads every Worker, then promotes callees first: publisher, ingest, control, query, ruler, mcp, gateway. Each class's schema version goes into the release record and onto every Worker version (D46). On the development branch control's OAuth signing key is also put on control's upload when it lacks one (D53).
  4. smoke.mjs waits until /healthz reports the new release, then writes a sample and reads it back.
  5. If the smoke test fails and the release has no migration, the previous release is restored automatically; with a migration it fails loudly, because the release is forward-only. A release is also forward-only when a class's compatibility floor rises, and a rollback is refused when any version that ran since its target wrote storage the target cannot open (D46). Format versions are not in that check yet.

Status: on main; first production deploy pending a repository secret. The workflows have not yet run on GitHub. The same scripts ran three times against staged copies on Cloudflare, the third with the publisher bound and with release records carrying schema versions (evidence below). The OAuth key that the development branch's deploy generates has not run there. deploy/README.md

The protocol model

Two models written independently, one in Quint checked with TLC and one explicit-state checker at the granularity of the code, explore every interleaving of append, seal, flush, admission, discard, compaction, retention, deletion, the orphan sweep and the loss of a shard's or a ledger's storage. Switching off any guard the design names produces a counterexample in both, so the models have teeth.

They found F1–F15. Two compaction findings (F13, and F14, which is critical), incarnation reuse (F11), a flush that filed a new incarnation's rows under the old one (F12) and a sweep that trusted an unlogged registration (F15) were fixed and re-checked: no counterexample to the ten safety invariants within bounds, up to 31 steps and about 19 million states. That is bounded, not exhaustive: at most 3 batches, 2 shards, 2 tenants and one fault of each kind, with shard-map changes not modelled.

A final run on 19 November checked the compaction rule (D30) and the segment log as built: both pass within bounds, the segment log exhaustively with three ledger losses (3.4 million states). Open on main: F6, both its liveness half (after a shard loses its storage nothing re-registers its stream, so its queries are refused) and F6(b) (one silently wrong answer), which registration before writes (F1) closes; and F8. spec/README.md

On the development branch the model goes further: F16, minor, an orphan compaction output that is never swept unless the tenant writes to that shard again; four variants of registration before writes and a fix for F16, checked in the model; a review of the recommended variant, which found 1 blocker, 2 majors and 9 minors and asked for it to be built with changes; and that variant being built (D61). spec/README.md and design/REVIEW.md, development branch

Open risks

  • The ledger's state limit. A tenant's ledger holds up to 300 MiB of state, about 300,000 live files, bounded by time, not memory: with checkpoints in parts (D47) its rebuild takes 20 s here, modelled 20–60 s on Cloudflare, the tenant refused meanwhile; the publisher re-bases such a tenant streaming, from the newest checkpoint or the base (D55), completing at 300,000 files with V8's heap capped below the isolate's 128 MB, in 8–17 s here (a first publication of them 27–38 s), not yet timed on Cloudflare against its CPU limit. Production keeps the cap at 16 MiB for this release. Until 2026-11-19 that was because the publisher read a new incarnation's base whole. Now it is because the release before cannot hold or checkpoint a larger state, so a rollback must not meet one, and because a rebuild and a first publication above 16 MiB have not been timed on Cloudflare against the CPU limit. A later release, whose rollback floor is this one, lifts it once they are. Above the cap addUnit answers full; flush retries, the tenant's shards fill and its senders get 429 until compaction or retention make room. Nothing alerts on it. ledger/README.md
  • F6, registration after the first write. A shard registers a new stream with the ledger only at its first flush. A stream that gets no new writes after its shard lost its storage is refused indefinitely. If a shard loses its storage while a query is between its plan and its tail read, and the stream was on its first unit, that query can silently miss a batch that is safe in a file: one wrong answer, not lost data, and rare. The fix, registering before the first write, spans shard, ledger, flush and query; it is not on main. On the development branch it was checked in the model, reviewed, and is being built (D61). spec/README.md F6
  • The tail-read wall. On main every query reads every shard's whole unflushed tail, and the tail counts against the 16 MiB fetch limit. Ten minutes of 100,000 series at 60 s is 20.2 MB, so every query of such a tenant was refused until a flush (measured here); a tenant spread over more than four to eight shards would be refused all the time (modelled). The shard's half of the fix, a filtered and paged tail read, is on main (D48); the query service on main does not use it, so there the wall stands. On the development branch the query service reads the tail filtered and paged (D54). CARDINALITY.md item 1
  • The pruning wall, in part. Series-level pruning (D41) answers a one-series query at 100,000 series that was refused before. Left: the query Worker resolves matchers only when the window's series files fit the fetch limit (about 120,000 series over an hour), so at 1,000,000 series a one-series query is still refused; split parts still read every series file whole; a selection spread across the id space, such as one namespace, still needs every row group. On the development branch split parts read only their id range of the series files (D59). CARDINALITY.md item 2
  • The ruler evaluates over HTTP, one query at a time. Fine for groups of tens of rules; a 1,000-rule group would hit its timeout until the query service exports an RPC entrypoint (D39).
  • Warm-ups and backtests are refused, not resumed (D51). At the default budgets a week of 1,000 series at 1 minute is refused, and so is the warm-up of a daily seasonal rule over 100 series at 5 minutes; that rule starts cold. The CPU prices behind the refusal are calibrated here, not on Cloudflare.
  • Refused recorded samples look like ingest errors. In Trial 3, refused RecordedSamples calls reached the caller correctly but ended as "hung" exceptions in ingest; not understood. On the development branch two release-skew paths have not been seen on Cloudflare: whether it accepts a ruler version bound to an entrypoint its ingest lacks (D52), and whether a rollback across the release that created the OAuth key is refused (D53); neither is documented or measured, and each has a staged experiment written down. deploy/README.md
  • Plans grow with file count (276 ms and 5.8 MB at 7,000 files, S4), and shard-map changes have no drain-and-handover yet, so pool changes that would move keys are refused. CPU fairness inside a pooled shard is unmeasured. DESIGN §13

Licence and clean-room engines

viz is Apache-2.0, chosen by the owner on 19 November (D35; LICENSE, NOTICE). The reference implementations of TraceQL and LogQL, Grafana Tempo and Loki, are AGPL-3.0, so viz's engines for both are written clean-room from the public documentation. Tempo v3.1.1 and Loki v3.7.10 are used only as black boxes at test time, their test suites are fetched at test time and never stored, and each crate's CLEANROOM.md lists every source consulted. Where Tempo's documentation is silent, viz follows its evaluator's observed behaviour, not its storage shortcuts (D40); where Loki's is silent, Loki's observed behaviour, departing only where Loki contradicts its own documentation or is inconsistent (D50). Both crates reached main through pull request #2, and the regex translator they share, also clean-room, through #4. An earlier TraceQL crate that transcribed and ported Tempo's code was removed and is not shipped.

Third-party material kept in the tree is listed with its obligations in THIRD_PARTY.md: Prometheus's test corpus (Apache-2.0) and a port of the NAB scorer (MIT); it also lists two fonts (SIL OFL 1.1) that the design system carries on the development branch. A dependency check found no copyleft package that ships.
