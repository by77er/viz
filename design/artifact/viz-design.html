Design brief · draft 3.1 · 18 Nov 2026

viz: an observability store that lives in one Cloudflare account

Metrics, logs and traces in Parquet on R2, published as Iceberg tables. PromQL and TraceQL on top. Dashboards and monitors that agents and people share. This page is the design, what the research found, how the design changed under review, and how it will be proven.

12 research tracks 3 independent reviews 1 benchmark run 0 lines of product code

Read this first

The product has not been built, and nothing has run on Cloudflare. One thing has been measured in a sandbox: the engine-language choice, below. Every other latency and cost figure is a model, printed as a range. My first cost table was wrong: a reviewer recomputed it against the design as drawn and the small-deployment figure went from $5.20 to $5–15, the team figure from $250 to $400–800. The first experiment in the plan decides where in those ranges reality sits.

The shape

For each tenant, one small ledger says which files exist. Everything else follows it.

LedgerOne Durable Object per tenant lists the live files of all that tenant's tables, plus a watermark per shard. It is the only authority on what is visible, and it can be rebuilt from a log on R2.
TailRows that were acknowledged but are not yet in a listed file are held by exactly one shard, in a write-ahead log.
SeamA query reads one ledger version, then asks each shard only for rows above its watermark. A shard that has already discarded those rows refuses, and the query re-reads the ledger. No silent gaps.
PublicationIceberg snapshots are produced from ledger changes every few minutes, for external engines. viz's own queries never wait on the catalog.

How the design changed under review

I gave the second draft to two reviewers who had not seen my reasoning and asked them to break it. They returned 57 findings, 11 of them critical. The third draft is a structural response.

A third reviewer then attacked only what was new in draft 3. It judged the core sound: the fenced seam, the contiguous watermark, and catalog independence. It found 12 problems at the edges, four of them critical, such as an index updated outside the ledger transaction and sequence numbers that were per shard when shards can be shared between tenants. Draft 3.1 amends the text for each. Those amendments have not been reviewed again; the next real check is the formal model, not another reading.

The parts

Write path

The edge Worker checks the API key and decodes OTLP or Remote Write into a columnar batch. The shard appends it to its log and answers only once that is durable. When full it answers 429; it never accepts and drops. Shards seal small segments; a stateless Worker turns each into one sorted Parquet file per table, and the ledger admits all of them in one transaction.

Storage

Seven tables: series, samples and rollups for metrics; spans and a trace index; logs. Every file holds one tenant, so retention and erasure are file drops. Compaction is time-ordered and keeps sort order. Rollups are written when an hour closes. viz is the only writer; managed compaction stays off.

Read path

Each language parses to its own tree and lowers to one plan. The tenant filter comes from the session and cannot be omitted. Leaves stream one row group at a time and return partial aggregates. Work that will not fit an isolate runs the identical engine in a Container.

One engine

A Rust core with no I/O does parsing, planning, Parquet and evaluation. It runs as WASM in Workers, natively in Containers, and inside a seeded simulator in CI. That last use is why it has no I/O.

Monitors

Prometheus rule semantics, extended to logs and traces. Each rule is classified when saved by what it has to read, and its cost is shown. Anomaly detection is statistics first. Agentic monitors run when a rule or anomaly fires, use read-only tools, and link every claim to the query behind it.

Dashboards

A small typed spec with stable panel ids. Edits are patches, dry-run against real data before saving. Every dashboard has a visual form, a text digest and a structured form from the same data; agents read the digest. About a dozen MCP tools, shared with the REST API. Prometheus and Tempo HTTP APIs are served, so Grafana works on day one.

Tenancy and auth

Tenant id comes only from the credential. Hashed, scoped API keys for machines; OAuth and single sign-on for people and agents. Small tenants share tables and shard pools; a tenant needing direct Iceberg access, residency or scale gets a dedicated cell.

Pull and adapters

Scrapers run on alarms and feed the same write path. Adapters share one contract in both directions with Arrow as the currency: poll an external system on ingest, or scan it at query time. First-party adapters ship first.

First measurement: Rust or JavaScript for the engine

The same encode and the same sum(rate(metric[5m])) query were implemented both ways over 1.92 million samples. Each side was tuned separately, each read the other's files, and all variants returned identical results to 12 digits.

WorkloadJavaScript, tunedRust as WASM, tunedRatio

The gap comes mostly from 64-bit integer decoding, which JavaScript has to route through BigInt. On the Rust side, tuning mattered as much as the language: keeping metric names dictionary-encoded and enabling WASM SIMD took the full scan from 73 ms to 32 ms.

Limits of this result: sandbox wall time, not billed CPU on Cloudflare. The local Workers runtime does not enforce the 128 MB limit. Both sides used snappy; the zstd build for WASM is untested. The Rust module holds one hard-coded query, so a full engine will be larger than 0.8 MB. I did not write a custom JavaScript decoder, which could narrow the integer gap.

How this gets verified

Two layers. The first is what I did to check this document. The second is what the system has to pass as it is built.

This pass

  • Independent researchers; facts several reached separately are treated as established.
  • Every claim tagged verified, secondary or training knowledge.
  • Six disagreements between researchers listed and resolved in writing.
  • Adversarial review of the draft, then a rewrite, then a re-review of the rewrite.
  • Every modelled number tied to an experiment with a kill criterion.

The system

  • Numbered invariants: an acknowledged row is durable, never lost, never doubled; no tenant reads another's data; results do not depend on where rows are stored.
  • A formal model of the seal, flush, ledger and publish protocol, with traces replayed against the code.
  • Deterministic simulation of the Rust core with injected faults.
  • The upstream PromQL test corpus, plus differential runs against real Prometheus and Tempo.
  • Every published snapshot read back by DuckDB and PyIceberg.
  • Cost as a test: CI fails when a change adds object reads or subrequests to a reference query.
  • In production, a canary tenant writes known data and reads it back continuously.

Decisions for you

  1. Who is the first user? I designed for deploying into your own account, with hosting unrelated tenants as an extension. If hosted is the goal, shared shard pools move from later to first.
  2. Iceberg a few minutes behind. Decided: accepted.
  3. Rust core. Decided: Rust, supported by the benchmark above. Still to check on Cloudflare itself: the enforced 128 MB limit, billed CPU, and a zstd build.
  4. Managed catalog second. I propose writing Iceberg metadata straight to R2 first and adding Cloudflare's managed catalog once a spike shows a Worker can commit to it reliably.
  5. Order of signals. Metrics, then traces and rules, then logs and detection.
