viz: an observability store that lives in one Cloudflare account

Metrics in Parquet on R2, published as Iceberg tables, with PromQL on top; TraceQL and LogQL engines built, their storage still proposed. Monitors and dashboards that agents and people share. This page is the architecture as built, what has been measured and how, what reviews and a protocol model changed, and what is still open.

The shape

For each tenant, one small ledger says which files exist. Everything else follows it.

LedgerOne Durable Object per tenant lists the live files of all that tenant's tables, plus a watermark per shard stream. It answers at its SQLite commit and writes its change log to R2 in batched segments, so it can be rebuilt from R2 alone.
TailRows that were acknowledged but are not yet in a listed file are held by exactly one shard, in a write-ahead log. Shards discard only what the ledger's R2 log already holds.
SeamA query reads one ledger version, then asks each shard only for rows above its watermark. A shard that has already discarded those rows refuses, and the query re-reads the ledger. No silent gaps.
PublicationIceberg snapshots are produced from the ledgers' logs every few minutes, for external engines. viz's own queries never wait on the catalog. Built and read back by two engines; not yet deployed.

The parts, as built

Write path

edge authenticates the key and decodes Remote Write 1.0 or OTLP metrics into columnar batches, routed by sender. A shard with 64 appends in flight or 16 MB pending refuses at once, before reading anything, with 503 and Retry-After; accepted appends share one SQLite transaction and each caller is answered after it (D37). A seal reaches flush through a queue, with a KV marker and an hourly sweep under it (D18). The ledger admits each flush unit in one transaction, answers, and drains its changes to R2 as one segment about 0.2 s later; shards discard only what is logged (D36). DESIGN §4

Storage and maintenance

Tenant-pure Parquet files for metric samples and series. A per-tenant maintenance run expires whole days (30 by default), merges files in a Worker (at most 16 MB per step, 70 MB of WASM memory measured), and deletes what the ledger calls deletable. A merge never deletes its outputs; each output records its inputs, and the sweep deletes an unlisted output only once an input is gone for good, with no clock involved (D30). An idle deployment wakes no object. DESIGN §5.2

Read path

One ledger read gives a version, its files and its watermarks; shards return rows above them or refuse. Files are read through leaf Durable Objects, each with its own six connections (D17). Aggregations split over leaves that each own a range of series keys and return exact partials, byte-identical to one place (D31). Series-level pruning reads only the row groups that hold a selected series (D41). /api/v1/plan reports what a query would read without reading it. query/README.md

Engines

A Rust core with no I/O, compiled to WASM: Parquet encode and decode, PromQL, split execution and the cardinality report. TraceQL and LogQL engines are separate clean-room crates checked against Tempo and Loki run as black boxes. They wait for spans and logs storage, which is proposed (contracts/TRACES.md, contracts/LOGS.md). engine/

Monitors

Ruler objects evaluate each group per tick through the query service's HTTP API with a service key that the tenant's control plane issues, one call in flight per object; recording rules write back through Remote Write (D39). Anomaly rules default to EWMA, or a static threshold for pages (D33). SLO rules raise the SRE Workbook's multi-window burn-rate alerts from one query per tick (D42). New rules are warmed from history under a planned budget, and backtests replay the same evaluation (D43). ruler/README.md

Delivery

One Notifier per tenant groups, inhibits and silences with Alertmanager's semantics and sends from a transactional outbox. Each body is built once and every attempt sends the same bytes under the same Idempotency-Key, signed with HMAC-SHA256. The destination (a webhook URL, viz's viz.notification/v1 or Alertmanager's JSON, a write-only secret) is set in control and offered as the receiver viz:default. A dead-man's-switch alert is built in. D39

Agents and control

control keeps keys, dashboards and their revisions, proposals, settings and an audit log in one Tenant object per tenant. mcp is a stateless MCP server with 13 tools, served also as JSON under /api/v1/agent through one dispatcher (D25–D27). Results fence tenant text as data and return usage counters (D28). Agents propose new dashboards and changes, and a person applies them (D29). The tenant comes only from the credential: an API key, or an OAuth access token that an MCP client gets from control after a person approves it with an admin key, never broader than that key (D44). mcp/README.md

Publication

One publisher object per cell writes Iceberg v2 metadata straight to R2, applying each tenant's ledger log strictly in version order and stopping at a hole rather than skipping it. The maintenance run nudges it and its own alarm publishes about two minutes later; an idle cell has no alarm (D34). It is built and tested, not yet bound in the write path or deployed; the managed catalog is undecided (S8). publisher/README.md

From a push to production

Every push to main deploys, so two releases always share storage for a while. Every Durable Object records a schema version and refuses storage newer than its code; formats that cross a release carry a version; readers deploy before writers (D24, UPGRADES.md).

  1. The checks of ci.yml run: both WASM engines built once, the Rust tests, and type checks and tests for each TypeScript component.
  2. deploy.sh ensures the bucket viz-lake, the KV namespace viz-config and four queues, and generates each Worker's configuration.
  3. release.mjs refuses a release whose Durable Object migrations no commit acknowledges, uploads every Worker, then promotes callees first: ingest, control, query, ruler, mcp, gateway.
  4. smoke.mjs waits until /healthz reports the new release, then writes a sample and reads it back.
  5. If the smoke test fails and the release has no migration, the previous release is restored automatically; with a migration it fails loudly, because the release is forward-only.

Status: merged to main; first production deploy pending a repository secret. The workflows have not yet run on GitHub. The same scripts ran twice against staged copies on Cloudflare (evidence below). deploy/README.md

The protocol model

Two models written independently, one in Quint checked with TLC and one explicit-state checker at the granularity of the code, explore every interleaving of append, seal, flush, admission, discard, compaction, retention, deletion, the orphan sweep and the loss of a shard's or a ledger's storage. Switching off any guard the design names produces a counterexample in both, so the models have teeth.

They found F1–F16. Two compaction findings (F13, and F14, which is critical), incarnation reuse (F11), a flush that filed a new incarnation's rows under the old one (F12) and a sweep that trusted an unlogged registration (F15) were fixed and re-checked: no counterexample to the ten safety invariants within bounds, up to 31 steps and about 19 million states. That is bounded, not exhaustive: at most 3 batches, 2 shards, 2 tenants and one fault of each kind, with shard-map changes not modelled. F6(b), with the registration rule F1 behind it, and F8 are open. spec/README.md

Open risks

  • The ledger's state limit (review S-2's guard). A tenant's ledger holds at most 16 MiB of state, about 15,800 live files, because a base or checkpoint is the whole state in one piece. Above it addUnit answers full; flush retries, the tenant's shards fill and its senders get 429 until compaction or retention make room. Nothing alerts on it. The full fix, a state written in pieces and a rebuild that streams into SQLite, is not built. ledger/README.md
  • F6(b), registration after the first write. A shard registers a new stream with the ledger only at its first flush. If a shard loses its storage while a query is between its plan and its tail read, and the stream was on its first unit, that query can silently miss a batch that is safe in a file: one wrong answer, not lost data, and rare. A stream that gets no new writes after a loss is refused indefinitely. The fix, registering before the first write, spans shard, ledger, flush and query and is not built; no code test covers it yet. spec/README.md F6
  • The tail-read wall. Every query reads every shard's whole unflushed tail, and the tail counts against the 16 MiB fetch limit. Ten minutes of 100,000 series at 60 s is 20.2 MB, so every query of such a tenant was refused until a flush (measured here); a tenant spread over more than four to eight shards would be refused all the time (modelled). The fix, a filtered and paged tail read in the shard, is not built. CARDINALITY.md item 1
  • The pruning wall. One series of a 100,000-series metric over an hour had a scan bound of 6.6 M samples, over the 3 M limit, so it was refused. Series-level pruning, which reads only the row groups holding the selected series, landed on 19 November (D41, query/README.md); CARDINALITY.md still lists it as open. A selection spread across the id space, such as one namespace, still needs every row group, and a compacted day file can make a one-hour query's bound too large.
  • The ruler evaluates over HTTP, one query at a time. Fine for groups of tens of rules; a 1,000-rule group would hit its timeout until the query service exports an RPC entrypoint (D39).
  • Plans grow with file count (276 ms and 5.8 MB at 7,000 files, S4), and shard-map changes have no drain-and-handover yet, so pool changes that would move keys are refused. CPU fairness inside a pooled shard is unmeasured. DESIGN §13

Licence and clean-room engines

viz is Apache-2.0, chosen by the owner on 19 November (D35; LICENSE, NOTICE). The reference implementations of TraceQL and LogQL, Grafana Tempo and Loki, are AGPL-3.0, so viz's engines for both are written clean-room from the public documentation. Tempo v3.1.1 and Loki v3.7.10 are used only as black boxes at test time, their test suites are fetched at test time and never stored, and each crate's CLEANROOM.md lists every source consulted. Where Tempo's documentation is silent, viz follows its evaluator's observed behaviour, not its storage shortcuts (D40). An earlier TraceQL crate that transcribed and ported Tempo's code was removed and is not shipped.

Third-party material kept in the tree is listed with its obligations in THIRD_PARTY.md: Prometheus's test corpus (Apache-2.0), a port of the NAB scorer (MIT) and two fonts (SIL OFL 1.1). A dependency check found no copyleft package that ships.

The interface

The design system is the ground truth for anything a person sees, and every change to it goes to a reviewer who did not write it (D16). Its review history: v1 and v2 rejected, v3 approved, v4 and v5 rejected. v5 fell on two blockers, series colour lost after a filter or an edit round trip and tables that scrolled the page sideways at 400 px and 200% zoom, plus seven majors. Version 6 answers every v5 finding and is in revision, not yet reviewed.

  • Flow screens: the first version was rejected; they now run on v5 and are to be re-imaged on v6.
  • The app: a metrics Explore view that runs against the real viz API, served locally, as well as a mock. Its restyle onto the system was rejected; the logic findings are fixed and the visual migration waits for the revised system. It is not part of the deployment, and its timings are not yet judged because the machine was overloaded.

Decisions for you

  1. The first production deploy. Open: add the repository secrets CLOUDFLARE_API_TOKEN and CLOUDFLARE_ACCOUNT_ID, then run the deploy with its migrations acknowledged (deploy/README.md, "One-time setup").
  2. Managed catalog. Open: S8 cannot run until the token has Workers R2 Data Catalog Write. Until then publication stays R2-native, which DuckDB and PyIceberg read.
  3. Licence. Decided: Apache-2.0, with clean-room TraceQL and LogQL (D35).
  4. Rust core. Decided, and S2 on Cloudflare widened the margin to 10–18× in billed CPU. Still open: a zstd build and sustained memory behaviour.
  5. Monitoring viz with viz. Proposed on your direction: one deployment, a viz-internal tenant, aimed at scaling and cost rather than outage alerts (D23). Not built.
  6. Earlier decisions stand: your own account first, with pooled shards (D13); Iceberg a few minutes behind (D2); metrics, then traces and rules, then logs and detection (D14).
