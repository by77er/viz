Design and status · DESIGN.md draft 3.1 · 28 Nov 2026

viz: an observability store that lives in one Cloudflare account

Metrics in Parquet on R2, published as Iceberg tables, with PromQL on top; spans and logs stored and published the same way and read through Tempo's and Loki's APIs by the TraceQL and LogQL engines, built on main behind flags that are off. Monitors and dashboards that agents and people share. This page is the architecture as built on main, what the development branch adds beyond it, what has been measured and how, what reviews and a protocol model changed, and what is still open.

Every number below says what kind it is: measured on Cloudflare (with date and runs), measured here on a shared development machine, or modelled. Costs and most latency targets are still models.

The shape

For each tenant, one small ledger says which files exist. Everything else follows it.

LedgerOne Durable Object per tenant lists the live files of all that tenant's tables, plus a watermark per shard stream. It answers at its SQLite commit and writes its change log to R2 in batched segments, so it can be rebuilt from R2 alone.
TailRows that were acknowledged but are not yet in a listed file are held by exactly one shard, in a write-ahead log. Shards discard only what the ledger's R2 log already holds.
SeamA query reads one ledger version, then asks each shard only for rows above its watermark. A shard that has already discarded those rows refuses, and the query re-reads the ledger. No silent gaps.
PublicationIceberg snapshots are produced from the ledgers' logs every few minutes, for external engines. viz's own queries never wait on the catalog. Read back by two engines; wired into ingest, which nudges it, and physical deletes wait for it.

The parts, as built

Write path

edge authenticates the key and decodes Remote Write 1.0 or OTLP metrics into columnar batches, routed by sender. A shard with 64 appends in flight or 16 MB pending refuses at once, before reading anything, with 503 and Retry-After; accepted appends share one SQLite transaction and each caller is answered after it (D37). A seal reaches flush through a queue, with a KV marker and an hourly sweep under it (D18). The ledger admits each flush unit in one transaction, answers, and drains its changes to R2 as one segment about 0.2 s later; shards discard only what is logged (D36). A checkpoint of a state over 1 MiB is written in parts across drains and a rebuild streams into SQLite, so no step holds the whole state (D47). viz-ingest also exports RecordedSamples, an entrypoint for the ruler's recorded samples whose service binding is the credential (D45). Since #9 edge also decodes OTLP traces, OTLP logs and Loki push behind a flag that is off, into shards of their own, and flush files them under the ledger like metric files (D57, D58, D63); what a decoder builds is bounded for every signal (D71); and a shard can refuse a new stream until the ledger has logged its registration (D61, off by default for one release). DESIGN §4

Storage and maintenance

Tenant-pure Parquet files for metric samples and series, and behind the flag for spans, their trace index and logs, which the same step compacts table by table (D68) and which expire by retention settings of their own (D63). A per-tenant maintenance run expires whole days (30 by default), merges files in a Worker (at most 16 MB per step, 70 MB of WASM memory measured), and deletes what the ledger calls deletable once the cell's publisher has released it too. A merge never deletes its outputs; each output records its inputs, and the sweep deletes an unlisted output only once an input is gone for good, with no clock involved (D30). An idle deployment wakes no object. DESIGN §5.2

Read path

One ledger read gives a version, its files and its watermarks; shards return rows above them or refuse. Files are read through leaf Durable Objects, each with its own six connections (D17). Aggregations split over leaves that each own a range of series keys and return exact partials, byte-identical to one place (D31). /api/v1/plan reports what a query would read without reading it. Series-level pruning reads only the row groups that hold a selected series (D41), and the shard can filter its tail by time, metric, label and key range and answer in pages (D48). Since #7 the query service reads the tail that way under one byte budget for all shards (D54), counts the label endpoints over leaves (D56) and gives split parts their id range of the series files (D59). Since #9 it also answers Tempo's and Loki's HTTP APIs behind a flag that is off: in one place, under a byte budget the engine charges before it makes each thing, a trace read whole within a margin around the window (D62). query/README.md

Engines

A Rust core with no I/O, compiled to WASM: Parquet encode and decode, PromQL, split execution and the cardinality report. The TraceQL and LogQL engines, merged through pull request #2, are clean-room crates checked against Tempo and Loki run as black boxes. TraceQL has a hand-written parser that refuses nesting deeper than 100 levels, and follows Tempo's evaluator where the documentation is silent, never its storage shortcuts (D40). LogQL runs its vector operations on the PromQL evaluator (D49) and follows Loki's observed behaviour where the documentation is silent (D50). Since pull request #4 both compile regexes in Go's dialect, as Tempo and Loki do, through one shared translator, engine/goregex. Since #9 they are linked into the read path's one WASM module and answer Tempo's and Loki's APIs over stored spans and logs and the shards' tails, behind a flag that is off (D62). engine/

Monitors

Ruler objects evaluate each group per tick through the query service's HTTP API with a service key that the tenant's control plane issues, one call in flight per object (D39). Anomaly rules that do not page default to the robust z-score with a quantile spread, which held its score on a second benchmark where EWMA, the earlier default, did not; pages default to a static threshold (D33, rewritten). Robust z and seasonal windows can be read as Float64 ring blocks, which a later release writes (D60, readers first). Since pull request #3, SLO rules raise the SRE Workbook's multi-window burn-rate alerts from one query per rule per tick (D42); new anomaly and SLO rules are warmed from history in memory-sized windows under budgets checked before anything is fetched, and backtests replay the same evaluation (D43); both are priced in CPU and refused whole over budget, never cut off by the platform (D51), and the refusal names the budget (rules contract version 5). Recorded samples go back through viz-ingest's RecordedSamples entrypoint over a service binding, with no key (D45), and through Remote Write only as a fallback for one release, when the entrypoint does not answer by its contract (D52). ruler/README.md

Delivery

One Notifier per tenant groups, inhibits and silences with Alertmanager's semantics and sends from a transactional outbox. Each body is built once and every attempt sends the same bytes under the same Idempotency-Key, signed with HMAC-SHA256. The destination (a webhook URL, viz's viz.notification/v1 or Alertmanager's JSON, a write-only secret) is set in control and offered as the receiver viz:default. A dead-man's-switch alert is built in. D39

Agents and control

control keeps keys, dashboards and their revisions, proposals, settings and an audit log in one Tenant object per tenant. mcp is a stateless MCP server with 14 tools, served also as JSON under /api/v1/agent through one dispatcher (D25–D27). One of them, backtest_monitor, is read-only and reports when a monitor would have fired and resolved, under the ruler's budgets. Results fence tenant text as data and return usage counters (D28). Agents propose new dashboards and changes, and a person applies them (D29). The tenant comes only from the credential: an API key, or, for an MCP client, an OAuth access token from control, granted after a person approves it with an admin key and never broader than that key (D44); the deploy generates control's client-signing key once and replaces it only when told to (D53). mcp checks each token through a control entrypoint that answers only that and takes the tenant from the token; it holds no binding to control's tenant objects, and a code or token without control's tag reaches none of them. Since #9 a credential carries its expiry, the Worker lists credentials its objects have called dead, and rate limits count each credential and then its tenant before any object is asked (D70). Production serves OAuth with these since 28 November (#9's release); the Rate Limiting bindings met Cloudflare on the S13 stage first. mcp/README.md

Publication

One publisher object per cell writes Iceberg v2 metadata straight to R2, applying each tenant's ledger log strictly in version order and stopping at a hole rather than skipping it (D34). viz-ingest binds it, every maintenance run nudges it, its own alarm publishes about two minutes later, and a removed file is deleted only once it releases it; Trial 3 ran this on Cloudflare. An idle cell has no alarm. It re-bases a tenant on a new ledger incarnation from its newest checkpoint (in parts) or its base, streaming into SQLite (D55): at 300,000 files it fits in about a third of the isolate's 128 MB, measured locally. A table whose cursor is below the checkpoint its tenant is read from is re-based with it, so no change in between is skipped: an adversarial review found that skip, and it is fixed. Since #9 it publishes all five tables, the span and log tables as Iceberg tables of their own with the metric tables' bytes unchanged (D67), and a re-base that does not fit one invocation goes on across invocations and commits once: at most about 5 s of CPU per publish at 300,000 files, measured locally (D55, amended, and reviewed). The managed catalog is undecided (S8). publisher/README.md

From a push to production

Every push to main deploys, so two releases always share storage for a while. Every Durable Object records a schema version and refuses storage newer than its code; formats that cross a release carry a version; readers deploy before writers (D24, UPGRADES.md).

  1. The checks of ci.yml run: both WASM engines built once, the Rust tests, and type checks and tests for each TypeScript component. They also cover app (type check, unit tests, the token check, the production build, and that build read by app/serve.json's rules as the deploy reads it) and design-system (its tests and its check without the rendered audit); nothing that needs a browser runs in CI. The web app is then built from an export of the commit's sources in a job that holds no secret, and handed to the deploy job as data.
  2. deploy.sh ensures the bucket viz-lake, the KV namespace viz-config and four queues, and generates each Worker's configuration.
  3. release.mjs refuses a release whose Durable Object migrations no commit acknowledges, uploads every Worker, then promotes callees first: publisher, ingest, control, query, ruler, mcp, gateway. Each class's schema version goes into the release record and onto every Worker version (D46). Control's OAuth signing key is also put on control's upload when it lacks one (D53).
  4. smoke.mjs waits until /healthz reports the new release, then writes a sample and reads it back.
  5. If the smoke test fails and the release has no migration, the previous release is restored automatically; with a migration it fails loudly, because the release is forward-only. A release is also forward-only when a class's compatibility floor rises, and a rollback is refused when any version that ran since its target wrote storage the target cannot open (D46). Since #9 format versions are in that check; a switch that lets new data in puts a rollback floor under every Worker that must read it; a rollback across the creation or a rotation of control's OAuth key is refused before anything moves (measured on Cloudflare, S9); one Worker can be rolled back alone with --only; and production deploys only from main, with main's tooling (D69).

Status: production was first deployed on 2026-11-19 from main at fb77292 (#8), by the owner, with that commit's tooling, and ran it until 2026-11-28. #9's release (375e9ba) went over it on 2026-11-28 through the Deploy workflow (run 46125868615, 08:27 to 08:36 UTC): /healthz then reported 375e9ba with every backend healthy, and OAuth's metadata and registration answered (measured on Cloudflare). That release is forward-only for viz-control (a rollback floor: #8's control mints credentials without an expiry); the other six Workers can each be rolled back alone with --only. Before it merged, the stage trial spikes/s13-upgrade-trial/ ran the same upgrade on Cloudflare: the six Rate Limiting bindings were accepted at upload and the version API lists them as type: ratelimit with namespace_id, the names the deploy reads. Since D75 the deploy gives the gateway both hostnames, viz first, and refuses a release that would detach one or touch another hostname of the zone; a stage's issuer is its own workers.dev URL. The same scripts ran three times against staged copies on Cloudflare before #9, the third with the publisher bound and with release records carrying schema versions (evidence below). deploy/README.md

The protocol model

Two models written independently, one in Quint checked with TLC and one explicit-state checker at the granularity of the code, explore every interleaving of append, seal, flush, admission, discard, compaction, retention, deletion, the orphan sweep and the loss of a shard's or a ledger's storage. Switching off any guard the design names produces a counterexample in both, so the models have teeth.

They found F1–F15. Two compaction findings (F13, and F14, which is critical), incarnation reuse (F11), a flush that filed a new incarnation's rows under the old one (F12) and a sweep that trusted an unlogged registration (F15) were fixed and re-checked: no counterexample to the ten safety invariants within bounds, up to 31 steps and about 19 million states. That is bounded, not exhaustive: at most 3 batches, 2 shards, 2 tenants and one fault of each kind, with shard-map changes not modelled.

A final run on 19 November checked the compaction rule (D30) and the segment log as built: both pass within bounds, the segment log exhaustively with three ledger losses (3.4 million states). It left F6 open, both its liveness half (after a shard loses its storage nothing re-registers its stream, so its queries are refused) and F6(b) (one silently wrong answer), which registration before writes (F1) closes; and F8, still open. spec/README.md

Since #9 the model on main goes further: F16, minor, an orphan compaction output that is never swept unless the tenant writes to that shard again; four variants of registration before writes and a fix for F16, checked in the model; a review of the recommended variant, which found 1 blocker, 2 majors and 9 minors and asked for it to be built with changes; and that variant built (D61). As built, a read or the janitor makes a shard register a fresh incarnation in every mode, which closes F6's liveness half and F16; F6(b) stays possible for appends until production runs the mode that refuses a new stream's writes until its registration is logged, which is off by default for this first release. spec/README.md and design/REVIEW.md

Open risks

  • Moving the address (D75). viz.bitcru.sh is the address; vis.bitcru.sh keeps the data paths, served with Deprecation and a successor Link, and answers everything else with a 308. OAuth clients connected through vis must reconnect: their tokens were issued for https://vis.bitcru.sh/mcp, which viz no longer accepts. A script that calls control, monitors or the agent API on vis must change its base URL, since most clients drop the credential when a redirect changes host. One thing the tooling cannot see: a DNS record that already exists for viz would be replaced by the first deploy, so the owner checks the zone first. deploy/README.md, "Hostnames"
  • Spans and logs at volume. Both flags are off in production. The trial on Cloudflare (S10) left four findings open: a compaction run was killed at the 30 s CPU limit; every trace query is refused above about 240,000 spans in an hour; a 4 KB request can cost edge 1.4–3.4 s of CPU to decode; and a stage's timers go on after its expiry. None is fixed. D62's fixes were re-checked and approved on 26 November, measured here; the query flag still waits for S10's realistic and fat shapes run again on Cloudflare with the current build, a Grafana run against a staged gateway, and the owner's acceptance of the stated ceilings, among them a log query that makes a series per line, refused at about 6,000 rows in its window. The fix that followed D72's review was re-checked and approved with changes, which are made; what a span or log read with a time range costs in rows read on Cloudflare (2 to 3 per batch in local workerd) is not measured. spikes/s10, query/README.md
  • The ledger's state limit. A tenant's ledger holds up to 300 MiB of state, about 300,000 live files, bounded by time, not memory: with checkpoints in parts (D47) its rebuild takes 20 s here, modelled 20–60 s on Cloudflare, the tenant refused meanwhile; the publisher re-bases such a tenant streaming, from the newest checkpoint or the base (D55), completing at 300,000 files with V8's heap capped below the isolate's 128 MB, in 8–17 s here (a first publication of them 27–38 s). Production keeps the cap at 16 MiB. Both were timed on Cloudflare since (S11): at 64 MiB a rebuild used 14.2 s of CPU and a first publication 5.6 s, at 150 MiB 16.4–18.6 s and 14.0 s, against a 30 s limit; 300 MiB was not run and extrapolates over it. So the cap can rise to 64 MiB and no further yet; that is not done. The publisher now re-bases a large tenant across invocations (D55, amended); the ledger's rebuild keeps no progress. Above the cap addUnit answers full; flush retries, the tenant's shards fill and its senders get 429 until compaction or retention make room. Nothing alerts on it. ledger/README.md
  • F6, registration after the first write, half closed. In production a shard still registers a new stream with the ledger only at its first flush. If a shard loses its storage while a query is between its plan and its tail read, and the stream was on its first unit, that query can silently miss a batch that is safe in a file: one wrong answer, not lost data, and rare. The fix, registering before the first write (D61), is on main since #9, checked in the model and reviewed. Its first release runs it off: only the half that needs no new refusal is on, so a stream whose shard lost its storage is registered again by the next read or by the janitor, and is no longer refused indefinitely. The other half turns on in the release after, once every edge maps the new refusal to 503. spec/README.md F6, shard/README.md
  • The tail-read wall, mostly down. Before #7 every query read every shard's whole unflushed tail, which counts against the 16 MiB fetch limit: ten minutes of 100,000 series at 60 s is 20.2 MB, so every query of such a tenant was refused until a flush (measured here). Since #7 the query service asks each shard only for what it needs, in pages, under one byte budget for all shards; a tail still too large is split by series id into at most 16 parts, each reading to an end fixed before the split, and past that the query is refused (D54). One series over a 21 MiB tail now reads under 1 KiB of it (measured here). Each part's shard still scans every batch it holds: 12–69 ms here for tails of 10.6 to 34 MiB, not measured on Cloudflare. CARDINALITY.md item 1
  • The pruning wall, in part. Series-level pruning (D41) answers a one-series query at 100,000 series that was refused before. Left: the query Worker resolves matchers only when the window's series files fit the fetch limit (about 120,000 series over an hour), so at 1,000,000 series a one-series query is still refused; a selection spread across the id space, such as one namespace, still needs every row group.   • The ruler evaluates over HTTP, one query at a time. Fine for groups of tens of rules; a 1,000-rule group would hit its timeout until the query service exports an RPC entrypoint (D39).
  • Warm-ups and backtests are refused, not resumed (D51). At the default budgets a week of 1,000 series at 1 minute is refused, and so is the warm-up of a daily seasonal rule over 100 series at 5 minutes; that rule starts cold. The CPU prices behind the refusal are calibrated here, not on Cloudflare.
  • Refused recorded samples look like ingest errors. In Trial 3, refused RecordedSamples calls reached the caller correctly but ended as "hung" exceptions in ingest; not understood. One release-skew path has not been seen on Cloudflare: whether it accepts a ruler version bound to an entrypoint its ingest lacks (D52); it is not documented or measured, and has a staged experiment written down. The other, a rollback across the release that created the OAuth key, was measured (S9): Cloudflare allows it and OAuth is left without a key, so the deploy now refuses it (D53, D69). deploy/README.md

Licence and clean-room engines

viz is Apache-2.0, chosen by the owner on 19 November (D35; LICENSE, NOTICE). The reference implementations of TraceQL and LogQL, Grafana Tempo and Loki, are AGPL-3.0, so viz's engines for both are written clean-room from the public documentation. Tempo v3.1.1 and Loki v3.7.10 are used only as black boxes at test time, their test suites are fetched at test time and never stored, and each crate's CLEANROOM.md lists every source consulted. Where Tempo's documentation is silent, viz follows its evaluator's observed behaviour, not its storage shortcuts (D40); where Loki's is silent, Loki's observed behaviour, departing only where Loki contradicts its own documentation or is inconsistent (D50). An earlier TraceQL crate that transcribed and ported Tempo's code was removed and is not shipped.

Cloudflare's catalog, SQL engine and streaming ingest went GA on 1 Oct 2026 under the name Basin. Catalog operations cost $9 per million.One table per tenant is ruled out on commit cost alone. Commits must be batched and skipped when nothing changed.verified ×6
The managed streaming ingest allows 20 streams per account, has a 60 s minimum roll, no sort control, and drops invalid events silently.viz writes its own Parquet. The managed pipeline is not on the path.verified ×4
The managed SQL engine caps results at 10,000 rows and has no Workers binding.PromQL and TraceQL need their own engine.verified
A Worker isolate has 128 MB including WASM, and only six connections may wait for headers at once.Small row groups, streaming evaluation, and leaves that are Durable Objects (confirmed by S1).verified
There is an open, unexplained corruption report against the managed catalog in which two writers disagreed.viz is the only writer to its tables, and the catalog is not the source of truth.verified
From 1 Dec 2026 Cloudflare sells its own logs and traces product at $0.25 per GB, without PromQL or TraceQL.viz differentiates on open formats, standard query languages, external sources and the agent surface.verified ×3
Tempo 3.0 and Loki 4.0 both moved to a durable log, one copy on object storage and stateless queriers.The overall shape matches where the incumbents ended up.mixed
AI investigation agents score 25–60% on published root-cause benchmarks, and prompt injection through log lines is demonstrated.Agentic monitors are advisory, read-only and never in the paging path.secondary
How rules are scheduled changes their cost by three orders of magnitude.Many rules per object, one tick. No Workflow per rule.modelled
